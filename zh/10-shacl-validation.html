SHACL 生成与验证：从数据长出的守门人

第 3 章学了 SHACL 理论、第 9 章学了本体怎么从数据推断——本章把两者接通： SHACLGenerator（ontology_generator.py:794）本体字典 → shapes 图， 再交给第 3 章验明正身的 run_shacl_validation()（pyshacl）检验数据。 这是 ontology 模块里工程质量最高的部分——注释里躺着 #1104/#1105 两个 真实教训：「假合格」陷阱和「无中生有的约束」，都值得慢慢读。

学习目标
  • 能复述 SHACLGenerator 的内部六步流水线及每步产物
  • 能解释继承传播（把父类 shapes 物化给子类）与 RDFS 类型上传的区别：物化 vs 推理
  • 能说出 quality_tier=strict 做什么（closed=True）以及为什么只关闭「至少有一个属性」的形状
  • 能讲清 #1104「假合格」陷阱：shapes 命名空间与目标命名空间为什么必须分开
  • 能独立走通「本体 → SHACL 生成 → 序列化 → pyshacl 验证」的完整治理闭环

10.1 SHACLGenerator：内部六步流水线

from semantica.ontology import SHACLGenerator, run_shacl_validation

gen = SHACLGenerator(
    base_uri="https://myco.dev/shapes/",        # shapes 自己住的命名空间
    target_namespace="https://myco.dev/ontology/",  # 被检验术语的命名空间（见 10.3）
    quality_tier="strict",
)
graph = gen.generate(ontology)          # → SHACLGraph
shacl_turtle = gen.serialize(graph, format="turtle")

类 docstring（798–805 行）自带路线图，六步内部流水线：

  1. _build_class_index() —— 类名 → 类 dict 的 O(1) 索引；
  2. _generate_node_shapes() —— 每个 OWL 类一个 NodeShape；
  3. _attach_property_shapes() —— 属性按 domain 挂到对应 NodeShape 上；
  4. _propagate_inheritance() —— 父类的属性形状复制给子类（迭代式、防环）；
  5. _apply_quality_tier() —— strict 档把所有（有属性的）形状设 closed=True；
  6. serialize() —— Turtle / JSON-LD / N-Triples。

第 3 章的理论词汇在这里全部有实体：dataclass PropertyShape（:733）的字段就是 sh:path / sh:datatype / sh:class / sh:minCount / sh:maxCount / sh:in / sh:pattern / sh:severity；NodeShape（:749）有 target_class / property_shapes / closed / severity。你在演示里玩过的迷你校验器，这里长成了完整实现。

两个数据结构细节见功力：SHACLGraph（:779）里 class_iris 与 property_iris 是分开的两张映射——注释解释：属性与类同名是合法的， 合一张表会静默地把类的 IRI 错配给属性；_mint_term_iri()（:763）给裸名字铸 IRI 时 做百分号编码——"Customer Account" 直接拼进 IRI 会有空格，严格解析器当场拒绝。

10.2 继承传播与质量档位

继承传播（_propagate_inheritance，:1148）值得单独讲： Employee 的必填属性 name，其子类 Manager 也该被检查。RDFS 的做法是推理时上传 （Manager ⊑ Employee ⇒ manager 实例也是 Employee ⇒ 套 Employee 的规则）； SHACL 的默认语义不做继承——所以生成器把父类的 PropertyShape 物化复制到每个子类形状里。「推理 vs 物化」是同一需求的两种工程解， 物化的好处是 shapes 图自包含（验证器无需理解本体层级），代价是图变大、 层级改动后要重新生成。迭代式实现 + 防环处理，对应第 9 章 DFS 环检测的同一担忧。

质量档位（_apply_quality_tier，:1170）是个聪明的开关： 

if self.quality_tier == "strict":
    for node_shape in graph.node_shapes:
        if node_shape.property_shapes:      # 只关「至少声明了一个属性」的形状
            node_shape.closed = True

strict 档打开第 3 章讲的封闭形状：没声明过的属性一律违规。 只关有属性的形状是个细致的防守：一个空形状（本体里只有名字没有属性的类） 如果 closed=True，会拒绝该类实例上的一切属性——误杀全部数据。 「默认开放、可选封闭、封闭只对有内容的形状」三段设计，读起来三行，想明白每行都得踩过坑。

10.3 两个命名空间的教训：#1104「假合格」与 #1105「无中生有」

⚠ #1104：shapes 打自己命名空间 = 全员假合格

构造器把 base_uri（shapes 资源住的命名空间，默认 https://semantica.dev/shapes/）和 target_namespace （被检验术语住的命名空间）刻意分成两个参数。docstring（:831–835）记录了原因： 如果 shapes 的 sh:targetClass 指向 shapes 自己的命名空间， 数据图里没有任何东西住在那里——shapes 匹配不到任何节点， 而 pySHACL 对「没检查任何东西」的报告是 conforms=true！

这是 SHACL 体系里最阴险的坑：验证器不会区分「全对」和「根本没检查」。 一个指向错误命名空间的 shapes 文件会给你一张绿色的假合格证。回归测试 tests/ontology/test_shacl_target_namespace.py 就是这个教训的纪念碑。 审读任何「合格」报告前，先确认 shapes 真的圈住了数据。

#1105：attach_domainless_properties 默认关——无中生有的约束

一个没有声明 domain 的属性该挂在哪？0.6.6 之前的行为：挂到每一个 NodeShape 上。听起来周到，实际是发明了本体从未说过的约束—— 某个 data 属性突然要求所有类的实例都遵守它的 datatype/minCount， 数据一入库集体爆违规。修复：参数保留但默认 False（:825，docstring :836–839）。 教训：生成器可以补默认值，但不能替本体立法。

另一个顺手可学的映射表：_XSD_ALIASES（:807–815）把宽松的类型别名归一到标准 XSD—— 注意 float/decimal → xsd:decimal 而不是 double（金融场景的取舍：decimal 精确、 double 是二进制浮点有误差），与第 9 章类型格的 double 并存不冲突——格管「合并拓宽」， 别名表管「拼写归一」。

10.4 完整闭环：生成 → 序列化 → 真验证

把第 8、9、10 章串成一条可运行的治理闭环（假设你已装 semantica[shacl]）： 

from semantica.ontology import (
    OntologyGenerator, SHACLGenerator, OWLGenerator, run_shacl_validation)

# ① 从 KG 字典生成本体（第 8-9 章；validate=False 跳过占位验证）
ontology = OntologyGenerator(base_uri="https://myco.dev/ontology/") \
    .generate_ontology(kg_dict, validate=False)

# ② 从本体生成 SHACL shapes（本章）
shacl = SHACLGenerator(
    base_uri="https://myco.dev/shapes/",          # shapes 的家
    target_namespace="https://myco.dev/ontology/", # 被检术语的家（#1104：必须分开）
    quality_tier="strict",
).generate(ontology)
shacl_turtle = SHACLGenerator().serialize(shacl, format="turtle")

# ③ 把数据图也序列化成 Turtle（第 2 章的 OWLGenerator/RDFExporter）
data_turtle = OWLGenerator().generate_owl(ontology, format="turtle")

# ④ 真验证（第 3 章的 run_shacl_validation —— pyshacl 路线）
report = run_shacl_validation(data_turtle, shacl_turtle)
print(report.summary())            # "Graph conforms…" 或违规计数
print(report.conforms, report.violation_count, report.warning_count)
for v in report.violations:
    print(v.focus_node, v.result_path, v.constraint, v.explanation)

注意闭环的哲学：本体从数据长出来（8–9 章），shapes 从本体长出来（本章）， 再回头检验数据（第 3 章的真验证器）。第一次跑通时数据大概率不合规—— 这不是失败，是治理循环的起点：违规清单告诉你修数据还是修本体，修完再跑。 与第 4 章方法论的「用 CQ 验证 → 迭代」同构，只不过这里用的是 SHACL 报告。

10.5 本章回顾

  • SHACLGenerator（ontology_generator.py:794）内部六步：类索引 → NodeShape 生成 → 属性挂载 → 继承传播 → 质量档位 → 序列化；PropertyShape/NodeShape 字段即第 3 章的 SHACL 词汇。
  • 继承传播是物化不是推理：父类属性形状复制进子类，shapes 图自包含； RDFS 类型上传 vs SHACL 无继承，两种解法一个需求。
  • strict 档 = closed=True，但只关「至少有一个属性」的形状（空形状 closed 会误杀一切属性）。
  • #1104：shapes 命名空间 ≠ 目标命名空间；指向自己的 shapes 匹配不到任何节点， pySHACL 报 conforms=true——「没检查」和「全对」在报告上长得一样。 #1105：无 domain 属性默认不挂到所有形状——生成器不能替本体立法。
  • 完整闭环：KG → 本体 → shapes → pyshacl 验证 → 违规清单驱动修复。 第一次不合规是常态，不是失败。
常见误区
  • 看到 conforms=true 就庆祝——先确认 shapes 圈住了数据（#1104 假合格）。
  • 把 base_uri 和 target_namespace 设成同一个——直接踩 #1104。
  • 打开 attach_domainless_properties 却不知后果——所有形状凭空多出约束，数据集体爆违规。
  • 对空形状开 closed——该类实例的一切属性都会违规，误杀全量数据。
  • 忘了 semantica[shacl] extra——run_shacl_validation 会 ImportError； 闭环第 ④ 步跑不起来。
  • 期望 SHACL 自动修复数据——它只报告；修复靠你或冲突解决策略（第 6 章）。
