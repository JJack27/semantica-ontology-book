Semantica 架构全景与核心抽象

从这章起，你从「本体领域学习者」切换到「semantica repo 的工程师」。 目标是建立那张脑内地图：27 个子包各管什么、数据长什么形状、 两个脊柱抽象（KG 字典和 ContextGraph）在哪里交接、 以及 ontology 模块在整个版图上的位置。有了这张地图，后面八章的精读才不会迷路。

学习目标
  • 能复述 Semantica 的一句话定位与完整流水线（九个阶段），并说出每个阶段对应的子包
  • 能按「摄取 → 清洗 → 抽取 → 质量 → 建图 → 智能 → 存储 → 输出」给 27 个子包归位
  • 能解释 KG 字典（{"entities": [...], "relationships": [...]}）的形状以及它为什么是全 repo 的通用货币
  • 能用 ContextGraph 的 add_node / add_edge / to_kg_dict / state_at 做基本操作，并指出各自源码位置
  • 能说出四种使用入口（Python API / CLI / REST / MCP）各自的适用场景

5.1 一句话心智模型

README 的自我介绍浓缩成一句：Semantica 是 LLM/向量库/智能体框架之下的 确定性基础设施层——把碎片化数据做成带类型、带约束、带溯源的知识图谱， 让每个 AI 决策可审计。关键定语是「确定性」：建图、推理、溯源都不需要 LLM 参与 （LLM 只是可选的抽取增强），这是它敢主打「监管级可问责」的底气。

整个系统是一条真实存在的流水线（ARCHITECTURE.md 有完整 Mermaid 图）， 每个阶段都是独立可导入的模块： 

Sources → Ingest → Parse → Normalize → Split → Extract → Conflict Detection → Dedup
   → Knowledge Graph → [ Ontology · Reasoning · Provenance · Decisions ] → Enriched KG
   → Vector Store + Graph Store (RDF & LPG) → Export / Visualize / REST · MCP · CLI

用第一部分的语言重读这条流水线：前半段（到 Knowledge Graph）是造「数据层」—— 把 PDF、数据库、网页变成实例三元组；方括号里四件套是造/用「模式层」—— ontology 从数据反推模式，reasoning 用规则扩知，provenance 给每个事实挂来源， decisions 把 AI 的选择变成一等公民节点；后半段是落地——多后端存储与全格式导出。 你学的前四章，恰好是方括号那格的理论底座。

有个结构事实值得单独记：本体版本管理（change_management）是独立子包， 而不是 ontology 的子模块——第 4 章提过的那次「搬家」。跨包引用时从 semantica.change_management 导入 VersionManager。

5.3 两个脊柱抽象：KG 字典与 ContextGraph

这个 repo 里所有模块交换数据，靠的是一个朴素到令人发指的形状—— KG 字典： 

kg = {
    "entities": [
        {"id": "acme_corp",  "type": "Organization", "name": "Acme Corp", "industry": "SaaS"},
        {"id": "alice_chen", "type": "Person",       "role": "CTO"},
    ],
    "relationships": [
        {"source": "alice_chen", "target": "acme_corp", "type": "works_for"},
    ],
}

用第一部分的话说：entities 的 type 是模式层概念的实例化， relationships 是实例层的边。ingest 产出它的原料、kg 模块组装它、 ontology 模块从它反推模式层、export 模块把它序列化成 Turtle/JSON-LD、 存储层把它写进图数据库——它是全 repo 的通用货币。注意键名的演变史坑： 早期版本 relationship 里用 source/target，导出适配用 source_id/target_id，README 特意提醒 to_kg_dict() 是官方适配器——别手拼字段。

另一个脊柱是 ContextGraph（semantica/context/context_graph.py:514， 整个文件 4000+ 行，是 repo 里最大的单类）。它是「带记忆、带决策、带时间旅行」的运行时图： 

from semantica.context import ContextGraph

graph = ContextGraph(advanced_analytics=True)

# 节点/边 —— context_graph.py:1077 / :1110
graph.add_node("acme_corp", "Organization", name="Acme Corp", industry="SaaS")
graph.add_edge("alice_chen", "acme_corp", edge_type="works_for",
               valid_from="2024-03-01", valid_until="2025-01-01")   # 带时间窗的边

snap = graph.state_at("2024-06-01")     # :3485  时间旅行：任意历史时点的图快照
kg   = graph.to_kg_dict()               # :3347  官方适配器 → 上面那个 KG 字典形状

两个抽象的分工：KG 字典是纯数据（dict/list，可序列化、可在模块间传递、 可喂给 OntologyGenerator）；ContextGraph 是运行时对象（带索引、带分析方法、 带决策记录、带 provenance 钩子）。to_kg_dict() 是两者的官方桥—— ContextGraph 世界流向流水线世界的那扇门。第三部分你会反复经过这扇门。

5.4 四种使用入口

入口位置适合谁

5.5 本章回顾

  • 定位：LLM 之下的确定性基础设施层；建图/推理/溯源不依赖 LLM——监管级可问责的来源。
  • 九阶段流水线：Ingest → Parse → Normalize → Split → Extract → Conflicts → Dedup → KG → 智能层 → 存储 → 输出；每阶段独立可导入。
  • 27 子包五分组：摄取/清洗、抽取/质量、建图、智能层（ontology 所在地）、存储/输出； 平台入口（cli/server/mcp/explorer）横跨全部；支撑层垫底。change_management 是独立子包。
  • KG 字典 {"entities", "relationships"} 是全 repo 通用货币； ContextGraph 是运行时图对象；to_kg_dict()（context_graph.py:3347）是官方桥。
  • 四入口：Python API（本书主线）、CLI、REST、MCP；Explorer 是可视化工作台。
常见误区
  • 手拼 KG 字典字段名——source/target 与 source_id/target_id 有历史演变； 要跨模块传递一律 to_kg_dict() 出来的形状。
  • 把 Semantica 当 LLM 包装器——它是确定性层，LLM 只是可选增强（llms 子包经 LiteLLM 接各家）。
  • 在 ontology 里找 VersionManager——它搬去了 change_management。
  • 以为必须跑整个流水线——每个子包独立可导入，只建本体不建图、只查图不建本体都合法。
  • 把 ContextGraph 和 KG 字典混为一谈——前者是带索引/分析/决策的运行时对象， 后者是可序列化纯数据；混淆会导致在错误层面传引用。
