开发环境与贡献地图：从读者到提交者

最后一章解决「接下来动手」：把环境跑起来、看懂测试地图、走通贡献流程， 并且——本书一路攒下的四个「文档 vs 代码」发现，此刻全部变成你的 PR 候选。 读完这章，你就是这个 repo 的专家了：不是背过 API 的那种，而是知道边界在哪、 知道哪里值得改的那种。

学习目标
  • 能从零搭好开发环境（dev extras + shacl extra）并跑通 tests/ontology/ 全部测试
  • 能说出 tests/ontology/ 六个测试文件各自守什么，以及 #1104 回归测试的位置
  • 能描述这个 repo 的贡献工作流（issue 优先、重复 PR 政策、多类型贡献）
  • 能把本书发现的四处「文档 vs 代码」落差转化为可执行的 PR 计划

13.1 本地环境：装、跑、体检

git clone https://github.com/<你的 fork>/semantica && cd semantica
python -m venv .venv && source .venv/bin/activate

pip install -e ".[dev,shacl]"     # dev=pytest 等；shacl=pyshacl（第 3/10 章的闭环要用）
semantica doctor                   # 体检：Python 版本、包版本、向量后端、配置文件

pytest tests/ontology/ -x -q       # 首跑：本体模块全部测试

三个工程细节值得知道：① extras 体系（pyproject.toml:101 起）是 这个 polyglot repo 的减重术——shacl（:121）、llm-all、graph-all、vectorstore-all…… 重依赖全部按需安装，核心包保持轻装；dev 环境的一体化安装清单在 :255（全家桶）。 ② CI 里跑命令时记得 SEMANTICA_DISABLE_PROGRESS=1（README 环境变量节）： 进度条只在交互终端输出，但保险起见显式关掉。③ pytest 配置在 pyproject.toml:283（testpaths=tests），仓库根目录直接 pytest 即可全量跑。 docker-compose.yml / docker-compose.dev.yml 在需要完整后端（图库、向量库）时用， 只玩 ontology 模块用不上。

文件行数守什么

读测试是读懂一个模块最快的方式——它们是「真实可执行的行为规格」。改 ontology 相关代码前， 先让这六个文件在你机器上绿；改完再跑一遍。特别是 test_shacl_target_namespace.py： 它断言的东西（shapes 圈错命名空间必须被识别为问题）直接对应第 10 章那个最阴险的坑。 另外 test_notebook_14.py 揭示了这个 repo 的一个好习惯：cookbook 示例也是被测代码—— 文档腐烂从示例开始，所以他们把示例钉进了 CI。

13.3 贡献工作流

CONTRIBUTING.md 的要点浓缩：issue 优先（先找/建 issue 再动手， 避免白干）；重复 PR 政策（同名 issue 下以首个合格 PR 为准——动手前扫一眼已有 PR）； 贡献类型远不止代码——文档、测试、bug 报告、cookbook 示例、教育内容都被明示欢迎； 提交前本地跑测试 + 可选的 pre-commit hooks。 流程：fork → clone → venv → pip install -e ".[dev]" → 改 → 测 → PR（关联 issue 编号）。

13.4 你的前三个 PR 候选（本书的发现清单）

精读一路，我们攒下了四处「文档 vs 代码」落差。它们不是 repo 的耻辱—— 是快速演进开源项目的常态，更是新专家最好的入场券（小、明确、有测试可写）：

  1. similarity_threshold：实现或删除（第 9 章）。参数收而不用。 方案 A：在 ClassInferrer 里实现真正的相似度合并（实体类型名嵌入或编辑距离过阈值合并）； 方案 B（更轻）：移除参数 + 修正 __init__.py 模块 docstring 里的宣传。 附带单测即可提交。
  2. OntologyValidator：接真验证或诚实降级（第 3、8 章）。方案 A：内部转调 run_shacl_validation（pyshacl 可选依赖，缺失时降级为结构检查并 warning）； 方案 B：把 consistent/satisfiable 从默认 True 改为 None（未检查）， 并同步修正 5/6 阶段的三处口径（generate_ontology docstring、进度消息、模块 docstring 的 HermiT/Pellet 措辞）。
  3. generate_ontology 的 5/6 阶段口径统一（第 8 章，可并入上一条）。 docstring 说 5 阶段、进度消息说 6 阶段、模块注释点名 HermiT/Pellet——统一成一种诚实表述。
  4. ReteEngine alpha 匹配器增强（第 7 章，较大）：README 自己承认匹配器从简。 需要先写「当前行为 vs 期望行为」的失败测试矩阵再动实现——适合作为进阶贡献。

每一条都有明确的验收标准（测试），都在你现在已经精读过的文件里。提 PR 前重读 13.3 的工作流：先搜有没有同题 issue/PR。

13.5 收官：专家自检清单

合上书之前，过一遍这份清单——每一条你都应该能不看笔记答上来：

  • 领域侧：三元组/IRI/字面量（1）；RDFS 五谓语与推理（2）；OWL 属性三分与公理（2）； SHACL shapes/报告/与 OWL 分工（3）；SKOS 定位（3）；CQ/复用/命名/粒度/版本化方法论（4）。
  • Repo 侧：九阶段流水线与 27 子包地图（5）；数据形状演变与双时间态（6）； 四件套协作（7）；六阶段生成的真实状态（8）；推断算法与参数真相（9）； SHACL 生成与两个 issue 教训（10）；治理生态与 N 元关系（11）；四个平台集成点（12）。
  • 专家的元技能：读代码不信宣传语；看到 consistent=True 先问是算的还是默认的； 序列化当安全边界；API 的持久化语义看存储类型不看名字；知道边界的能力才是可用的能力。

你要的两个「expert」现在是一件事：本体领域的概念你都能在这个 repo 里指出对应的那行代码； 这个 repo 的每个模块你都能说出它在领域版图上的位置。这就是双专家的含义。 接下来：把 13.4 的 PR 候选做掉一个——从读者变成提交者，专家身份才算落章。

常见误区
  • 裸装包就跑 SHACL 闭环——pyshacl 在 shacl extra 里，记得 pip install -e ".[dev,shacl]"。
  • 改代码不跑 tests/ontology/——六份测试是这个模块的行为快照，跳过等于盲改。
  • 不搜重复 PR 就开工——同名 issue 下已有合格 PR 时你的工作会被礼貌地关闭。
  • 一口气想修大东西——从文档/口径统一这类小而确定的 PR 建立信任，再上算法级改动。
