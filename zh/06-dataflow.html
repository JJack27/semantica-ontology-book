端到端数据流：从 PDF 到 Turtle

上一章是地图，这一章是路书：我们跟着三份「真实」合同文档， 走完摄取 → 规范化 → 分块 → 抽取 → 冲突检测 → 去重 → 建图 → 导出的全程， 每一步都给出数据形状的变化和对应的真实 API。第一部分埋的两颗种子 （实体同一性、逻辑矛盾检测）会在质量关卡那节发芽；双时间态这个 Semantica 招牌能力， 本章讲透。

学习目标
  • 能复述数据在流水线每个节点上的形状（文档 → 分块 → 实体/关系 → KG 字典 → Turtle）
  • 能说出 entity_aware 分块为什么对 GraphRAG 至关重要，以及抽取后端（ml/pattern/llm）的选择逻辑
  • 能解释五类冲突（值/类型/关系/时间/逻辑）和三种仲裁策略（credibility_weighted / most_recent / voting）
  • 能描述 blocking + 语义相似度的去重两步法，以及为什么合并必须保留 provenance
  • 能解释双时间态（valid time vs recorded time）并手工判断「某查询日哪些事实可见」

6.1 故事线与全景图

设定：目录 ./contracts/ 里躺着三份文档——acme_master_2024.pdf（主协议）、 acme_amendment.pdf（修订案，估值变了）、globex_intro.docx（另一家公司的简介）。 目标：把它们变成一张带溯源的 KG，最后导出 Turtle。全程如下：

6.2 摄取与规范化

from semantica.ingest import FileIngestor

docs = FileIngestor().ingest_directory("./contracts/", recursive=True)
# → [{path, text, metadata…}, …]   统一形状，后续阶段不再关心原始格式

摄取层的全部使命是消灭格式差异：PDF、DOCX、HTML、CSV、数据库表、网页、 Kafka 流、Databricks 表……进来是什么不要紧，出去一律是「带元数据的文本/记录列表」。 之后流水线每一段都只认这个形状。

规范化（semantica.normalize）处理「人类写法」造成的脏：TextNormalizer 清 Unicode/智能引号/HTML 标签；EntityNormalizer 做别名归一 （"ACME Corp." → 规范名 + 置信度）；DateNormalizer 解析「三周前」这类自然语言日期； NumberNormalizer 把 "$1.25M USD" 变成 1_250_000 + 币种。 别小看这一步——第 9 章你会看到，本体类推断的质量直接吃规范化的红利： 类型字段不归一，频率统计就是垃圾进垃圾出。

6.3 分块与抽取：为图而切，为图而抽

传统 RAG 分块按字数切，切完送去嵌入。Semantica 的分块（semantica.split） 多一个心眼：别把实体和关系切碎。entity_aware 方法先做 NER 再切块， 保证命名实体不跨块；relation_aware 保证 (主语,谓语,宾语) 三元组同块； 还有 graph_based（按中心性找社区边界）、ontology_aware（第 12 章展开）等十余种。 为什么值得：下游的 GraphRAG 检索以「实体所在块」为召回单元，实体被切断 = 关系证据被切断。 

from semantica.split import TextSplitter
from semantica.semantic_extract import NamedEntityRecognizer, RelationExtractor

chunks = TextSplitter(method="entity_aware", chunk_size=1000).split(docs[0]["text"])

ner  = NamedEntityRecognizer(confidence_threshold=0.7)     # 置信度阈值砍掉低质实体
ents = ner.extract_entities(docs[0]["text"])
# → [Entity(name="Acme Corp", type="ORG"), Entity(name="Alice Chen", type="PERSON"), …]

rels = RelationExtractor(confidence_threshold=0.6, bidirectional=True).extract_relations(text, entities=ents)
# → [Relation(subject="Alice Chen", predicate="ceo_of", object="Acme Corp"), …]

一个工程要点：抽取有三种后端——ml（本地模型，默认，无需 API key）、 pattern（规则/正则）、llm（经 LiteLLM 调各家大模型）。 GraphBuilder.build() 的文档字符串（kg/graph_builder.py:422-462）写得很清楚： 默认全走本地，「Raw-text extraction uses local extractors by default and needs no provider or API key」——LLM 是可选项而非依赖项，呼应「确定性基础设施」的定位。

6.4 两道质量关卡：冲突检测与去重

我们的示例数据正好各踩一关：主协议说 Acme 估值 1.0B，修订案说 1.2B（值冲突）； 一份文档写 Acme Corp，另一份写 ACME Corporation（同一实体两个写法）。 流水线在它们进图之前各设一道关卡。

第一关：冲突检测（semantica.conflicts）。五类冲突：

类型例子
值冲突 value估值 1.0B vs 1.2B（同一字段不同值）
类型冲突 type一个来源说它是 Organization，另一个说是 Product
关系冲突 relationshipA 说 alice worksFor acme，B 说 worksFor globex
时间冲突 temporal同一事实的时间窗互相打架
逻辑冲突 logical违反互斥公理：同一人同时是 Manager 和 Intern（第 2 章 disjointWith 的工程化）
 
from semantica.conflicts import ConflictDetector, ConflictResolver, SourceTracker

conflicts = ConflictDetector().detect_conflicts(all_entities)
# → [Conflict(entity="acme", field="valuation", values=["1.0B","1.2B"], severity="HIGH")]

tracker = SourceTracker()
tracker.register_source("master_2024.pdf", credibility_score=0.9)   # 主协议更权威
tracker.register_source("amendment.pdf",  credibility_score=0.85)

resolved = ConflictResolver().resolve_conflicts(conflicts, strategy="credibility_weighted")
# 其他策略：most_recent（信最新的）、voting（多数票）

注意设计哲学：检测和仲裁分离。ConflictDetector 只报Conflict （带 severity），裁决权在 ConflictResolver 的策略里，而策略需要的事实（谁更可信） 由 SourceTracker 的可信度分数提供。监管场景偏爱这种结构——裁决理由可查。

第二关：去重/实体解析（semantica.deduplication），第 1 章的 ACME 之问在这里落地：

from semantica.deduplication import DuplicateDetector, EntityMerger

detector = DuplicateDetector(similarity_threshold=0.75, use_clustering=True)
groups   = detector.detect_duplicate_groups(entities)
# → [DuplicateGroup(entities=["e1","e2","e3"], confidence=0.91, strategy="semantic+blocking")]

merger   = EntityMerger(preserve_provenance=True)     # ← 关键开关
merged   = merger.merge_duplicates(entities, strategy="keep_most_complete")
history  = merger.get_merge_history()

两步法：blocking 先用廉价键（如域名、首字母桶）把 N×N 比较砍成近邻块 （CHANGELOG 记录过 63.6% 的候选生成提速），块内再算语义相似度（嵌入）， 过阈值成组。preserve_provenance=True 必须开着：合并后的实体要记得 「我由 e1、e2、e3 合并而来，各自来自哪个文件」——否则下次审计就断了线索。 这就是「provenance-preserving merge」，README 反复强调的产品级细节。

6.5 GraphBuilder：组装知识图谱

from semantica.kg import GraphBuilder, BiTemporalFact

kg = GraphBuilder(merge_entities=True, enable_temporal=True).build(docs)
# → {"entities": […], "relationships": […], "metadata": {…}}

build()（kg/graph_builder.py:422）的输入非常宽容：原始文本、 预抽取的实体对象、或现成的 KG 字典都收；串文本进来时它会按 extract/ner_method 等选项自动过抽取层。merge_entities=True 挂上 EntityResolver （别名表 + 相似度），enable_temporal=True 打开双时间态。 产物仍是 KG 字典——通用货币再次现身。

6.6 双时间态：世界时间 vs 认知时间

单时间轴的图回答不了监管场景的典型问题：「2024 年 6 月 30 日，我们当时认为 Acme 的估值是多少？」和「2024 年 6 月 30 日，事实上估值是多少？」是两个问题。 Semantica 的 BiTemporalFact（kg/temporal_model.py）给每个事实两根轴：

  • valid time（valid_from / valid_until）：事实在世界里为真的区间 ——合同 3 月 1 日生效、12 月 31 日到期；
  • recorded time（recorded_at）：这个事实进入你的系统的时刻 ——估值 6 月就定了，但 9 月才录进图里。

查询时两个轴独立过滤：state_at(date)（context_graph.py:3485）回答 「date 那天（且只统计 date 前已知的事实）图长什么样」；TemporalGraphQuery.query_time_range (kg, query="valid_facts", start, end) 回答「世界时间落在窗口内的事实」。 配套还有 TemporalNormalizer（「上个季度」→ 起止区间）和 README 特性表里的 Allen 区间代数（13 种区间关系）。对本体读者的意义：本体管「什么类型的事实」， 双时间态管「事实何时为真、何时可知」——第 11 章讲版本管理时这组概念会再次出现。

6.7 本章回顾

  • 形状演变链：文件 → 净文本 → 分块 → 实体/关系列表 → KG 字典 → RDF 三元组； 摄取层的使命是消灭格式差异，规范化是抽取与推断质量的地基。
  • 分块为图服务：entity_aware / relation_aware 保证实体与三元组不被切断——GraphRAG 的召回单元。
  • 抽取三后端：ml（默认、本地、零依赖）/ pattern / llm（可选增强）——「确定性」定位的体现。
  • 两道质量关卡：冲突检测五类（值/类型/关系/时间/逻辑）+ 三仲裁策略（credibility_weighted / most_recent / voting），检测与仲裁分离；去重两步法（blocking 砍比较量 + 语义相似度过阈值）， 合并必须 preserve_provenance=True。
  • 双时间态：valid time（世界为真区间）× recorded time（进入系统时刻）两轴独立； state_at / query_time_range 分别按两轴查询。
  • GraphBuilder.build()（graph_builder.py:422）输入宽容（文本/对象/字典），输出永远是 KG 字典。
常见误区
  • 跳过规范化直接抽取——类型/日期/数字不归一，第 9 章的类推断直接垃圾进垃圾出。
  • 把冲突仲裁交给默认策略不管——策略选择（credibility vs recency vs voting） 是业务决策，默认值不该替你做监管级决定。
  • 合并重复实体时丢 provenance——省下的存储换不回审计线索。
  • 把 valid time 和 recorded time 混为一谈——「当时事实上如何」和「当时我们以为什么」 是两个查询，双时间态的全部意义就在于此。
  • 按字数分块再建图——实体切断后关系抽取质量雪崩；建图场景永远优先 entity_aware。
