描述语言栈：RDFS 与 OWL

第 1 章的三元组只能表达「一个个孤立的事实」。这一章给图装上语义： RDFS 教会机器「类有层级、属性有归属」，OWL 再加上公理与推理。 这是本体领域的核心语言栈——也是 Semantica 的 OWLGenerator（semantica/ontology/owl_generator.py）真正生成的东西。

学习目标
  • 能读懂并手写 RDFS 的五个核心谓语：rdf:type、rdfs:subClassOf、rdfs:subPropertyOf、rdfs:domain、rdfs:range
  • 能手动执行 RDFS 推理：给定 subClassOf 链和实例数据，推出所有隐含的 rdf:type
  • 能区分 OWL 的三类属性（ObjectProperty / DatatypeProperty / AnnotationProperty）并说出各自的用途
  • 能解释至少四种 OWL 公理（subclass、equivalentClass、disjointWith、property 特征如 transitive/functional）各管什么
  • 能说清 OWL 子语言（DL / RL / EL / Full）在表达力与推理成本之间的权衡
  • 能对照 Semantica 的 OWLGenerator 源码，指出它输出了哪些 OWL 构件、没输出哪些

2.1 RDFS：给图装上最薄的语义层

RDF 三元组本身没有「类」的概念——你可以写 ex:alice ex:worksFor ex:acme， 但没有任何机制说明「alice 是一个人」「worksFor 是一种雇佣关系」。 RDFS（RDF Schema）就是解决这个问题的最薄一层语言：它本身也是一组三元组， 用一套预定义的谓语来谈论你自己的类和属性。核心只有五个：

谓语读作作用
rdf:type「是…的实例」把一个资源挂到一个类上：ex:alice rdf:type ex:Person
rdfs:subClassOf「是…的子类」声明类层级：ex:CTO rdfs:subClassOf ex:Manager（多重继承合法）
rdfs:subPropertyOf「是…的子属性」属性层级：ex:worksFor rdfs:subPropertyOf ex:affiliatedWith
rdfs:domain「主语必须是」属性的所属类：ex:worksFor rdfs:domain ex:Person
rdfs:range「宾语必须是」属性的取值类：ex:worksFor rdfs:range ex:Organization

这些谓语真正厉害的地方不是「声明」，而是它们自带推理规则。三条最重要的：

  • 类型上传：若 C rdfs:subClassOf D 且 x rdf:type C， 则 x rdf:type D。子类的实例也是父类的实例。
  • subClassOf 传递：若 C ⊑ D 且 D ⊑ E，则 C ⊑ E。 层级链条自动闭合。
  • domain/range 归属：若 p rdfs:domain C 且 x p y， 则 x rdf:type C。谁用了这个属性，谁就「被是」这个类。
最容易被误解的一点：domain/range 不是校验！

关系数据库直觉里，「worksFor 的 domain 是 Person」听起来像外键约束——写错了就拒绝入库。 RDFS 的语义完全相反：它是加事实的规则，不是拒绝数据的规则。 一个「错误」的 ex:toaster ex:worksFor ex:acme 不会报错， 只会让推理机得出「烤面包机是人」这个结论。要做「校验并拒绝」，得用第 3 章的 SHACL—— 这也是为什么 Semantica 在 OWL 之外还实现了一整套 SHACL 生成与验证（第 10 章）。

2.2 OWL：真正的本体语言

RDFS 能表达「层级」和「归属」，但很多领域知识它无能为力：「Manager 和 Intern 不可能同时成立」（互斥）」「parent 是传递关系」「每个人最多有一个 biologicalMother」（函数性）」 「Acme 和 ACME Corporation 是同一家公司」（等价）。这些是 OWL（Web Ontology Language）的领地。OWL 在 RDFS 之上扩展了一套公理词汇， 让机器可以推出你从未显式写下的事实，甚至发现矛盾。

先看属性的三个种类（OWL 要求你在生成时就分清，Semantica 的生成器也是按这个三分的）：

  • owl:ObjectProperty —— 宾语是资源的关系：worksFor、 partyTo。对应 KG 里的「边」。
  • owl:DatatypeProperty —— 宾语是字面量的属性：hasTitle（字符串）、 valuation（xsd:long）。对应 KG 里节点的「属性字段」。
  • owl:AnnotationProperty —— 元数据标注：rdfs:label、rdfs:comment。 不参与推理，纯粹给人看。

再看最常用的一批 OWL 公理（掌握这些，你就能读懂 90% 的工业本体）：

公理意思能推出什么
A rdfs:subClassOf BA 是 B 的子类（OWL 沿用）实例类型上传（同 RDFS）
A owl:equivalentClass BA 和 B 是同一个类双向类型互推
A owl:disjointWith BA 和 B 互斥：没有东西能同时属于两者检测矛盾（一致性检查的基石）
x owl:sameAs yx 和 y 是同一实体（第 1 章见过）属性在 x/y 之间互推
p rdf:type owl:TransitivePropertyp 传递（如 ancestor）a p b, b p c ⇒ a p c
p rdf:type owl:SymmetricPropertyp 对称（如 knows）a p b ⇒ b p a
p rdf:type owl:FunctionalPropertyp 函数性：每个主语最多一个宾语a p b, a p c ⇒ b sameAs c
p owl:inverseOf qp 和 q 互逆（worksFor / employs）a p b ⇒ b q a
owl:cardinality / owl:minCardinality属性取值个数限制条数不足/超标 → 不一致或补全

一个组合拳的例子。声明：ex:Manager owl:disjointWith ex:Intern， 然后某个数据源说 ex:dave rdf:type ex:Manager，另一个说 ex:dave rdf:type ex:Intern。没有任何一条数据单独是错的， 但推理机可以把两条放在一起推出 owl:Nothing（矛盾）——本体让你拥有 「跨来源发现逻辑冲突」的能力。Semantica 把这个思路产品化成了 semantica.conflicts 的「logical conflict」检测（第 6 章）。

2.3 对照真码：Semantica 的 OWLGenerator 输出什么

读一段真实源码。semantica/ontology/owl_generator.py 的 OWLGenerator._generate_with_rdflib()（第 210–328 行）把一个本体字典变成 rdflib 图， 核心映射就三步： 

# semantica/ontology/owl_generator.py:243-263（节选，注释为本书所加）
classes = ontology.get("classes", [])
for cls in classes:
    class_uri = URIRef(cls.get("uri") or gen_ns_manager.generate_class_iri(class_name))
    g.add((class_uri, RDF.type, OWL.Class))            # ← 每个类：a owl:Class
    ...
    if subclass_of:                                    # ← 层级：rdfs:subClassOf
        g.add((class_uri, RDFS.subClassOf, parent_uri))

# 第 267–316 行：属性分两支
if prop.get("type") == "object":                       # ← 关系 → owl:ObjectProperty
    g.add((prop_uri, RDF.type, OWL.ObjectProperty))
    for domain in domains:
        g.add((prop_uri, RDFS.domain, domain_uri))     # ← domain/range 公理
    for range_val in ranges:
        g.add((prop_uri, RDFS.range, range_uri))
elif self._is_datatype_property(prop.get("type")):     # ← 属性字段 → owl:DatatypeProperty
    g.add((prop_uri, RDF.type, OWL.DatatypeProperty))
    range_uri = self._resolve_datatype_range_uri(range_val, ...)  # ← xsd:string 等
    g.add((prop_uri, RDFS.range, range_uri))

也就是说，Semantica 生成的 OWL 目前覆盖语言栈的中间地带：OWL 类 + RDFS 层级与 domain/range + 属性三分。而上一节表里的高阶公理——disjointWith、传递性、基数限制、 等价类——不在这条主生成路径上。这不是坏事，而是「从数据自动生成」路线的合理剪裁： 你能从数据频率里可靠推断出「有哪些类、谁连谁」，但数据本身很少能告诉你「Manager 和 Intern 互斥」—— 那类领域公理需要人（或 LLM 辅助的 LLMOntologyGenerator，见第 11 章）来补。 读这本书时要养成习惯：看到文档说「支持 OWL」，要问清楚是 OWL 的哪个子集。

另一个值得注意的工程细节：OWLGenerator 在 rdflib 缺失时会退化为 _generate_basic()（第 330–413 行）——手工拼 Turtle 字符串。两条路径输出语义等价的东西， 但字符串版没有经过 rdflib 的语法校验。这种「优雅降级 + 明确警告日志」的模式在 Semantica 里很常见 （构造函数第 90–93 行的 warning）。

2.4 OWL 子语言：表达力与推理成本的账单

OWL 公理不是免费的。公理越多，推理（算出所有隐含三元组）的计算成本越高，某些构造甚至让推理 不可判定（理论上算不完）。W3C 因此切出了几个子语言（profile）， 各自在表达力和可计算性之间划线：

子语言定位推理成本典型用途
OWL DL完整描述逻辑，表达力强（全量公理 + 限制）可判定但可能很慢（EXPTIME 级）医学/生物本体（SNOMED、GO 用其变体）
OWL RL面向规则的子集：公理都可改写成「if-then」规则多项式，可流式推理工业 KG 的事实补全—— Semantica 的 Rete/前向链推理（第 7 章）走的就是这个思路
OWL EL面向大规模类层级：只要 subClassOf 类构造多项式且对大本体友好巨型医学术语库（SNOMED CT）
OWL Full不限构造，类可以是实例不可判定研究；生产几乎不用

给你一个工程直觉：「多少公理」是可以谈预算的。项目起步时用 RDFS + 少量 OWL RL 公理（传递、domain/range），推理用规则引擎就能跑；真有医学级需求再上 DL 推理机 （HermiT、Pellet 这类基于 tableau 算法的 Java 推理机）。Semantica 的选择是前者——它的推理模块 （前向链、Rete、Datalog）都是确定性规则推理，不依赖外部推理机服务； 本体文档里提到第 6 阶段「符号验证（HermiT/Pellet）」，那部分实际怎么实现的，第 8 章精读源码时会 对着代码验证——先卖个关子：文档和实现之间有值得注意的落差。

2.5 序列化：同一张图，多种皮肤

最后一个基础概念：三元组集合（图）与序列化格式是两回事。 同一张图可以写成四种常见格式，彼此完全等价、可无损互转：

格式长相什么时候用
Turtle（.ttl）前缀 + 缩写，人类最可读日常读写本体；Semantica 的默认输出
RDF/XMLXML 标签嵌套，啰嗦老系统交换（W3C 最早标准）
JSON-LDJSON + @context 把键映射成 IRIWeb/JS 生态、API 传输
N-Triples每行一条完整三元组，无缩写流式处理、diff、大数据量导出

对应到代码：OWLGenerator._generate_with_rdflib() 最后的序列化分支 （owl_generator.py:319-328）就是 g.serialize(format="turtle" | "xml" | "json-ld" | "n3") ——rdflib 一个 Graph 对象，换 format 参数就换皮肤。第 12 章讲导出时你会看到同一模式贯穿 semantica.export.RDFExporter。 

# 同一个事实，四种皮肤（内容完全等价）：
# Turtle
ex:alice ex:worksFor ex:acme .

# N-Triples（无前缀，全部展开）
<https://example.org/alice> <https://example.org/worksFor> <https://example.org/acme> .

# JSON-LD（@context 负责把短名映射回 IRI）
{ "@context": {"worksFor": "https://example.org/worksFor"},
  "@id": "https://example.org/alice", "worksFor": {"@id": "https://example.org/acme"} }

# RDF/XML（略——最啰嗦的那种，知道存在即可）

2.6 本章回顾

  • RDFS 五谓语：rdf:type、subClassOf、subPropertyOf、 domain、range；自带推理规则（类型上传、传递、domain/range 归属）。
  • domain/range 是推理规则不是校验约束——错误的用法会「推出」事实而不是被拒绝； 校验要靠 SHACL（下一章）。
  • OWL 属性三分：ObjectProperty（资源→资源）、DatatypeProperty（资源→字面量）、 AnnotationProperty（元数据）；公理覆盖等价、互斥、传递/对称/函数性、基数、sameAs。
  • 公理组合能发现矛盾（disjointWith + 两个来源的类型冲突）——跨源一致性的理论根基。
  • 子语言是预算：OWL RL（规则可算、工业 KG 主流）< OWL DL（强但贵）< OWL Full（不可判定）。 Semantica 选择规则推理路线。
  • 图 ≠ 序列化：Turtle / RDF-XML / JSON-LD / N-Triples 完全等价； Semantica 默认 Turtle，rdflib 一个调用换格式。
  • Semantica 的 OWLGenerator 实际输出 OWL 类 + RDFS 层级 + domain/range + 属性三分， 高阶公理不在自动生成主路径上——「支持 OWL」要问子集。
常见误区
  • 把 domain/range 当外键约束用——期望脏数据被拒绝，实际得到「被推出错误类型」的更多事实。
  • rdfs:subClassOf 写成环（A ⊑ B ⊑ A）——RDFS 推理会把 A、B 变成逻辑等价类而不是报错； Semantica 的层级构建专门做了 DFS 环检测（第 9 章）。
  • 混用 ObjectProperty 和 DatatypeProperty——把字面量接到 ObjectProperty 上在 OWL DL 里是不合法图。 Semantica 靠属性推断时的宾语类型判断走哪支（第 9 章）。
  • 以为必须用 OWL Full 才「完整」——Full 不可判定；生产默认从 RL/EL 起步。
  • 把 Turtle 当成「另一种 JSON」—— Turtle 的 ; , 是缩写糖， 解析后每条都是独立三元组；图才是本体。
