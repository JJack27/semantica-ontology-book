Chapter 1 · 第一部分：本体领域基础

本体论：从哲学到知识工程

摸底时你说「全都不懂」——很好，这是最诚实的起点。这一章从零开始： 什么是本体（ontology）、它和数据库表结构、知识图谱分别是什么关系、 以及 RDF 三元组这个「最小的知识原子」。读完这一章，你在摸底里没做出来的 三道题，应该全部能做对。

学习目标
  • 能用自己的话说出「本体」在知识工程中的定义，以及它从哲学概念演变而来的脉络
  • 能把一句自然语言事实（如「Alice 在 Acme 担任 CTO」）拆解成 RDF 三元组，并写出对应的 Turtle 片段
  • 能解释 IRI、字面量、空白节点各自的角色，以及为什么谓语必须用全局标识符
  • 能说清「两个数据源里的 ACME Corporation 是不是同一家公司」这个问题在 RDF 世界里靠什么机制回答
  • 能在具体场景里判断：该用数据库 schema、本体，还是知识图谱——以及它们如何叠在一起用

1.1 什么是本体：从「存在之谜」到「机器可读的世界观」

「本体论」（ontology，注意小写 o）原本是哲学的一个分支，研究的问题是 「什么东西存在，存在的都是什么类别」。亚里士多德在《形而上学》里讨论的 「实体与范畴」，就是在给世界做分类：物质、性质、数量、关系……哲学家们争论了两千多年 「什么是真实存在的」。

到了 1980–90 年代，人工智能研究者遇到了一个很实际的难题：要让两台机器（或两个软件系统） 交换关于世界的知识，光把数据传过去没用——还得让双方对「数据在说什么」达成一致。 于是哲学的 ontology 被借了过来，首字母大写成 Ontology（本体），含义变成了一个 工程术语。学界最常用的定义来自 Studer 等人对 Gruber 定义的综合：

本体的经典定义

「对某个概念化的显式的、形式化的规范」 （an explicit, formal specification of a conceptualization）。

拆开看：概念化（conceptualization）= 你心智模型里对世界的那套抽象（公司、人、雇佣关系）； 显式（explicit）= 白纸黑字写出来，不能靠意会； 形式化（formal）= 用机器能处理的严格语言写（不是散文）； 规范（specification）= 它是一份约定/规格，不是数据本身。

一个具体的本体回答的是这样一组问题：这个领域里有哪些类（Person、Organization、Contract）、 类之间什么关系（Manager 是 Employee 的子类）、有哪些属性 （worksFor、hasTitle、signedOn）、属性有什么规矩（worksFor 的主语必须是 Person、 宾语必须是 Organization；一个人同时最多任职几家公司……）。

为什么 AI 时代这件事突然重要了？因为 LLM 智能体恰恰缺这个。向量数据库存的是「相似性」， 不存「意义」：它知道「Acme 合同」和「Alice 的雇佣协议」这两段文本向量距离近， 却不知道 Alice worksFor Acme、Acme partyTo 合同 这样的结构化事实，更没法回答 「这份合同牵涉的公司的 CTO 是谁」。Semantica 这个 repo 存在的意义就是补上这一层—— 它的 semantica.ontology 模块（本书第三部分的主角）能把杂乱数据自动生成本体， 让智能体的上下文从「一堆相似度」变成「一张有类型、有约束、可推理的图」。

1.2 RDF 三元组：最小的知识原子

本体要用「形式化的语言」写，这个语言家族的地基叫 RDF（Resource Description Framework，资源描述框架），是 W3C 在 1999 年标准化的。RDF 的全部核心只有一个想法， 小得惊人：

RDF 的唯一核心思想

一切知识都表示成三元组（triple）： 主语（subject）— 谓语（predicate）— 宾语（object）。 主语是一个资源（thing），谓语是它和宾语之间的关系或属性，宾语是另一个资源或者一个字面值。 一条三元组 = 一句「主-谓-宾」的原子陈述。

「Alice 在 Acme Corp 担任 CTO」用三元组写出来就是两条： 

主语        谓语         宾语
─────────────────────────────────────────────────
ex:alice    ex:worksFor  ex:acme          ← alice 任职于 acme（宾语是资源）
ex:alice    ex:hasTitle  "CTO"            ← alice 的头衔是 "CTO"（宾语是字面量）

这里 ex: 是命名空间前缀（下一节细讲），它把 alice 展开成一个全局唯一的标识符。先别管细节，抓住两个要点：

  • 宾语分两种：指向另一个资源（另一条三元组的主语候选，如 ex:acme），或者是一个字面量（literal，字符串、数字、日期，如 "CTO"）。字面量是「死胡同」——没有东西能再从它出发指向别处。
  • 谓语不是字符串，它也是一个标识符（准确说一定是 IRI）。这一点是 RDF 和 JSON 字段名最本质的区别，1.3 节展开。

三元组的标准文本写法叫 Turtle（.ttl 文件），也是 Semantica 导出本体和 KG 的默认格式 （semantica.export.RDFExporter 输出的就是它）。上面那两条三元组的 Turtle 写法： 

@prefix ex: <https://example.org/> .        # 声明前缀 ex 指向这个命名空间

ex:alice  ex:worksFor  ex:acme ;           # 分号 = 同一个主语，下一条谓语宾语
          ex:hasTitle  "CTO" .              # 句点 = 这组陈述结束

注意 Turtle 里 ex:alice 这种写法是缩写，完整形式是尖括号包住整个 IRI： <https://example.org/alice>。分号让你复用主语，逗号复用主语和谓语—— 这只是语法糖，解析之后每条都是独立的三元组。

1.3 IRI、字面量与空白节点：标识符为什么是一切的基础

摸底第一题的四个选项，差别全在一个问题上：用什么标识「Alice」「worksFor」「Acme」这些东西。 RDF 的答案分三种成分：

  • IRI（Internationalized Resource Identifier，国际化的资源标识符）—— 形如 https://example.org/alice 的全局唯一名字。主语和谓语必须是 IRI； 宾语可以是 IRI 也可以是字面量。
  • 字面量（literal）——带类型的值："CTO"、 "250000"^^xsd:integer、"2024-01-15"^^xsd:date。只能当宾语。
  • 空白节点（blank node，写作 _:b1）—— 「有个东西但我暂时不想/没法给它起全局名字」。只能在一个文档范围内使用，细节本章先不展开， 你只要知道它是第三种成分。

为什么谓语不能用 "works_for" 这种普通字符串？设想两个团队各自导出一份数据： 

团队 A：("alice", "works_for", "acme")           # 字符串谓语
团队 B：("alice_chen", "works_for", "acme_corp")   # 也是字符串谓语

两份数据放在一起，机器看到两个一模一样的 "works_for"，但没有任何依据判断 它们是不是同一个意思——A 的 works_for 可能指「现任职」，B 的可能指「曾任职」。字符串只有字形， 没有归属。而 IRI 是全局唯一的： 

团队 A：ex:alice   <https://schema.org/worksFor>  ex:acme
团队 B：ex:alice   <https://schema.org/worksFor>  ex:acme   ← 同一个 IRI = 同一个含义

只要两个团队都引用 https://schema.org/worksFor（Schema.org 是一个公开的通用词表）， 机器就能确定：这是同一个谓语，两份数据可以无缝拼接。这就是摸底第一题选 B 的原因—— 三个成分都是 IRI（宾语也可以是字面量），谓语尤其必须是 IRI，否则跨数据集互通无从谈起。 「IRI 是全球坐标，字面量是本地便签」——记住这句话。

为了可读性，RDF 用命名空间前缀缩写 IRI。社区沉淀了一批约定俗成的公共命名空间， 你在本书和 Semantica 源码里会反复见到：

前缀命名空间管什么
rdf:http://www.w3.org/1999/02/22-rdf-syntax-ns#RDF 自身的基础词汇（rdf:type 等）
rdfs:http://www.w3.org/2000/01/rdf-schema#类层级与属性标注语言（第 2 章主角）
owl:http://www.w3.org/2002/07/owl#Web 本体语言——公理与推理（第 2 章主角）
xsd:http://www.w3.org/2001/XMLSchema#字面量的数据类型（xsd:string、xsd:integer…）
skos:http://www.w3.org/2004/02/skos/core#知识组织系统/词表（第 3 章主角）
schema:https://schema.org/Schema.org 通用词表（公司、人、事件…）
foaf:http://xmlns.com/foaf/0.1/「朋友的朋友」人物词表
prov:http://www.w3.org/ns/prov#溯源 PROV-O（第 7 章会用到）

Semantica 的本体模块里有一个专门的 NamespaceManager （semantica/ontology/namespace_manager.py）负责生成、校验、绑定这些前缀—— 第三部分精读它。

1.4 实体同一性：ACME Corporation 与 Acme Corp.

摸底第三题是行业里天天发生的真问题：Salesforce 里存 ACME Corporation， 年报 PDF 里印 Acme Corp.，招聘网站上写 Acme。它们是同一家公司吗？

在关系数据库里，你会建一张 companies 表，用自增主键 id=42 保证同一性——前提是入库前有人（或某段 ETL 代码）判断过 「这三名字是同一家」。同一性是建表时就定死的内部约定，跨库之后失效：另一家公司的 id=42 是完全不同的实体，JOIN 语义靠外键，而外键只在同一个库内有意义。

在 RDF 里，思路反转：

  • 名字只是属性。schema:name 是一个普通的谓语，一个实体可以有 一堆名字（法定名、简称、曾用名），它们是挂在同一节点上的字面量，谁也不覆盖谁；
  • 同一性由 IRI 承载。如果两个来源对同一实体恰好用了同一个 IRI，图自动缝合； 如果用了不同 IRI（ex:acme 和 salesforce:account_881）， 图里就是两个节点——直到你显式地声明它们相同。

「显式声明相同」的标准武器是 OWL 的等价公理：owl:sameAs： 

ex:acme                owl:sameAs  <https://salesforce.example/account_881> .
ex:acme                schema:name "ACME Corporation", "Acme Corp." .   # 两个名字并存
<…account_881>         schema:name "Acme Corp." .

但注意：RDF 不会自动发现 ex:acme 和 account_881 该被 sameAs——发现这个事实的过程叫实体解析（entity resolution）/ 实体对齐， 它是一个独立的工程问题：靠名字相似度、域名、地址等信号计算置信度，超过阈值才合并。 这正是 Semantica 里 semantica.deduplication 模块 （DuplicateDetector + EntityMerger，语义相似度 + blocking 策略） 和 semantica.conflicts 模块（两来源说法打架时的检测与仲裁）存在的意义。 本书第 6 章会把它们放进数据流里讲。

1.5 本体 vs 数据库 schema vs 知识图谱

摸底第二题问「表结构表达不了什么」，答案有三个（类层级继承、属性形式化语义、等价性公理）， NOT NULL 和主外键反而是关系数据库的强项。展开讲。

数据库 schema（表结构）回答的是「数据长什么样才能入库」：列名、类型、 非空、唯一、外键。它的世界是封闭世界（closed world）：表里没有的行就是不存在的， 外键指不到就是不合法。本体回答的是「这个领域的概念如何互相联系、可以推出什么」： 类层级、属性的 domain/range、等价/传递/对称公理。它的世界是开放世界（open world）： 没写出来的东西不是假的，只是「还不知道」——因为本体面对的是无穷的、永不完整的真实世界。

封闭世界 vs 开放世界（一个实验说清）

问：「Alice 有没有 manager？」 SQL 世界：employees 表里 Alice 的 manager_id 为 NULL → 她没有 manager（表是全部事实）。 本体世界：图里没有 alice 的 managesMe 边 → 目前不知道——也许有，只是还没录入。 这不是谁对谁错，是两种语义约定。混用它们是知识工程项目最常见的 bug 来源之一。

把三者的分工列成对照表（这大概是全书你会翻回来看得最多的一张表）：

数据库 schema本体（OWL）知识图谱（数据层）
回答什么数据入库的形状约束领域概念的形式化语义具体的事实实例
基本单元表、列、行类（Class）、属性（Property）、公理（Axiom）三元组（实例层的节点和边）

知识图谱不是第三种并列的东西，而是「本体（模式层）+ 实例数据（数据层）」的组合： 一张遵循某本体规定的节点和边。Semantica 里对应的就是那个贯穿全 repo 的字典形状 {"entities": [...], "relationships": [...]}——entities/relationships 的 type 字段（"Person"、"Organization"、"works_for"） 就是模式层概念的实例化。第 5 章你会看到 GraphBuilder 如何从文档生成它， 第 8 章你会看到 OntologyGenerator 如何反过来从这些数据推断出模式层。

1.6 本章回顾

  • 本体 = 对概念化的显式、形式化规范；在 AI 系统里它是机器可读的世界观， 位于「现实世界 → 概念化 → 本体（模式层） → 实例数据（数据层）」的第三层。
  • RDF 三元组（主语-谓语-宾语）是最小的知识原子；多条三元组通过共享 IRI 缝合成图。 Turtle 是最常见的文本写法。
  • 成分规则：主语、谓语必须是 IRI；宾语可以是 IRI 或字面量；空白节点是免命名的第三种成分。 「IRI 是全球坐标，字面量是本地便签。」
  • 谓语用 IRI 而非字符串，是为了跨数据集互操作：同一 IRI = 同一含义，合并即取并集。
  • 同一性由 IRI 承载，名字只是属性；跨来源发现同一实体需要显式的实体解析 （owl:sameAs / deduplication），RDF 不自动合并。
  • 本体（开放世界、公理推理）与数据库 schema（封闭世界、形状强制）互补； 知识图谱 = 本体 + 实例数据。
常见误区
  • 「本体 = 类图 / ER 图」——类图和 ER 图没有形式化语义，不能推理。 能推出隐含事实（Manager 是 Employee → Alice 是 Manager 则 Alice 是 Employee）才算本体。
  • 「RDF 是 XML」——RDF 是数据模型（三元组集合），XML 只是它众多序列化格式之一 （还有 Turtle、JSON-LD、N-Triples）。日常写 Turtle。
  • 「RDF 会自动合并相似名字」——不会。名字是字面量属性；同一性要么靠相同 IRI， 要么显式声明/解析。期待自动合并是新人最常见的翻车点。
  • 「开放世界里没查到 = 不存在」——本体的语义是「不知道」。 把 SQL 直觉带进 OWL 推理会得出错误结论。
  • 「有了 KG 就不需要本体」——没有模式层的图只是节点汤：类型混乱、无法验证、 无法推理。这正是 Semantica 要从数据反向生成并治理本体的原因。
