SHACL 约束与 SKOS 词表

第 2 章留下一个悬念：RDF/OWL 只会「推出事实」，不会「拒绝数据」。可真实系统偏偏需要 「入库前校验：名字必填、类型必须是整数、取值必须在允许集合里」。 SHACL（Shapes Constraint Language）补上这块拼图； SKOS则解决另一个朴素需求——不用完整 OWL，只想要一套受控词表。 这两个 W3C 标准恰好都是 Semantica 实打实实现了的（也有一个实现与文档有落差的地方，本章会点破）。

学习目标
  • 能读懂并手写一个 SHACL NodeShape + PropertyShape，用 minCount / datatype / sh:in / sh:pattern 表达常见约束
  • 能解释 SHACL 校验报告的结构（focusNode / resultPath / sourceConstraintComponent / resultSeverity）
  • 能说清 SHACL 与 OWL 公理的分工：校验（找违规） vs 推理（补事实）
  • 能对照 Semantica 源码指出：run_shacl_validation 是真实现（pyshacl），OntologyValidator.validate 是占位实现
  • 能用 SKOS 的核心词（Concept / prefLabel / broader / ConceptScheme）组织一套主题词表，并知道它和 OWL 本体的分工

3.1 为什么需要 SHACL：RDF 世界缺的「约束检查」

把第 2 章的结论推到极端：一个只讲推理的世界里，任何数据都是「合法」的。 烤面包机 worksFor 公司？推理机只会耸耸肩，推出「烤面包机是人」。但在生产系统里， 数据有明确的形状要求：一家 Organization 必须有名字、估值必须是整数、 类型必须落在允许集合里。你需要一个东西，它看着数据图说「这不符合约定」， 并且指出谁、在哪个属性上、违反了哪条约束、有多严重。

W3C 2017 年标准化的 SHACL（Shapes Constraint Language）就是干这个的。 它的思路：你写一组形状（shapes）——「某个类的节点应该长什么样」的声明—— 校验器（validator）拿形状去比对数据图，产出一份校验报告（也是一张 RDF 图）。 三个关键概念：

  • NodeShape：约束的靶子——「哪些节点要被检查」（通常 sh:targetClass 指向一个类）。
  • PropertyShape：约束的内容——「这些节点的某个属性（sh:path）必须满足什么」。
  • 约束组件（constraint component）：具体检查项——minCount、datatype、sh:in、pattern、closed……

3.2 读写 Shapes：一个完整例子

下面是一份约束 + 一份数据。先看约束（习惯上也写成 Turtle）：

@prefix sh:  <http://www.w3.org/ns/shacl#> .
@prefix ex:  <https://example.org/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

ex:OrganizationShape a sh:NodeShape ;
    sh:targetClass ex:Organization ;          # 谁被检查：所有 rdf:type ex:Organization 的节点
    sh:closed true ;                          # 封闭形状：没声明过的属性一律不许有
    sh:ignoredProperties ( rdf:type ) ;       # （rdf:type 豁免）
    sh:property [
        sh:path ex:name ;                     # 属性路径：ex:name
        sh:minCount 1 ;                       #   至少 1 个值（必填）
        sh:maxCount 1 ;                       #   至多 1 个值（单值）
        sh:datatype xsd:string ;              #   必须是字符串
    ] ;
    sh:property [
        sh:path ex:valuation ;
        sh:datatype xsd:long ;                #   必须是整数
    ] ;
    sh:property [
        sh:path ex:industry ;
        sh:in ( "SaaS" "Fintech" "Health" ) ; #   取值必须在允许集合里
        sh:severity sh:Warning ;              #   违反它只算警告，不算错误
    ] .

再给两个待检的数据节点：

ex:acme  a ex:Organization ; ex:name "Acme Corp" ; ex:valuation "1200000000"^^xsd:long ; ex:industry "Blockchain" .
ex:ghost a ex:Organization ; ex:hometown "Roswell" .          # 没有 name，还有多余属性

校验后你会得到一份报告（同样是 RDF，这里给出人读版本）：

[Violation] ex:ghost   path=ex:name       MinCountConstraintComponent     至少需要 1 个值，实际 0
[Violation] ex:ghost   path=ex:hometown   ClosedConstraintComponent       封闭形状不允许未声明属性
[Warning]   ex:acme    path=ex:industry   InConstraintComponent           "Blockchain" 不在允许集合中

四件事值得盯住：

  • 每一行违规就是一个四元组：谁（focusNode）、哪个属性（resultPath）、 违反了哪类约束（sourceConstraintComponent）、多严重（resultSeverity）。 这个结构是 SHACL 规范定义的，所有实现都得输出它。
  • severity 分三档：sh:Violation（违规，conforms=false）、 sh:Warning、sh:Info。后两档不把整个报告判为不合规—— 「业界不在允许集合」值得人看一眼，但不该挡住整批数据。
  • sh:closed 是「封闭形状」：没在 shape 里声明的属性一律报错。 这是把数据库「列必须先声明」的封闭性带进 RDF 世界的开关——第 1 章讲的开闭世界之辨， 在这里以每个 shape 为粒度重新拿回了主动权。
  • SHACL 不改数据。它只报告，不修复、不推理、不加三元组。 想修复要么自己写代码，要么走冲突解决（第 6 章）。

3.3 SHACL vs OWL 公理：一对好搭档的分工

新手最常见的困惑：「OWL 的 owl:cardinality 不也能限制个数吗？要 SHACL 干嘛？」 区别在语义方向：

  • OWL 基数是解释数据的公理：如果 alice 有两个 biologicalMother， OWL 推出的结论是「这两个母亲是同一个实体」（owl:sameAs）——它相信数据，去补全世界。
  • SHACL 基数是审视数据的约束：同样场景，SHACL 直接报告 MaxCountConstraintComponent 违规——它相信约定，去挑数据的刺。

3.4 对照真码：一个真实现，一个占位实现

Semantica 里 SHACL 有两条代码路径，成熟度天差地别——这是读源码比读 README 值钱的地方。

真实现：run_shacl_validation()（semantica/ontology/ontology_validator.py:148-273）。 它调用 pyshacl.validate()（Python 的 SHACL 标准实现），然后把 pyshacl 返回的 RDF 结果图解析成结构化的 SHACLValidationReport：

# semantica/ontology/ontology_validator.py:194-217（节选）
conforms, results_graph, results_text = pyshacl.validate(
    data_g, shacl_graph=shacl_g, inference="none", abort_on_first=False)

SH = rdflib.Namespace("http://www.w3.org/ns/shacl#")
for result in results_graph.subjects(rdflib.RDF.type, SH.ValidationResult):
    focus = str(results_graph.value(result, SH.focusNode) or "")        # ← 谁违规
    path  = results_graph.value(result, SH.resultPath)                  # ← 哪个属性
    sev   = str(results_graph.value(result, SH.resultSeverity))         # ← 多严重
    src   = results_graph.value(result, SH.sourceConstraintComponent)   # ← 哪类约束

你刚才在演示里玩的 focusNode / path / 约束组件 / severity 四元组，就是这里逐字段抽出来的。 实现还很贴心：按 severity 分桶（violations / warnings / infos），并回查源 shape 里的 minCount / datatype / class 真实参数，给每条违规生成一句人话解释 （explain_violations()，第 82–135 行，模板包括 MinCount/MaxCount/Datatype/Class/In/Pattern/Closed 七种）。 注意它依赖 pyshacl，没装会抛 ImportError 提示 pip install semantica[shacl]—— extra 依赖，默认不装。

⚠ 文档 vs 代码：OntologyValidator.validate() 是占位实现

README 的 ontology 示例展示的是另一个类：OntologyValidator().validate(ontology) 返回 ValidationResult(valid=True, consistent=True, satisfiable=True, ...)。 打开源码（ontology_validator.py:326-382）你会发现： 

# 第 340-354 行，原文如此
# Placeholder implementation for now
# In a real implementation, this would load owlready2 or similar
...
if self.check_consistency:
    # Logic to check consistency would go here
    pass                              ← 一致性检查：什么都不做
if self.check_satisfiability:
    pass                              ← 可满足性：同样什么都不做

构造参数 reasoner="hermit" 被接受但从未使用；check_constraint() 恒返回 True（第 381 行注释自己承认是 placeholder）。 也就是说 ValidationResult 里那个 consistent=True, satisfiable=True 是默认值，不是检查结论——真正的检查只有「字典里有没有 classes/properties 键」这一条结构性提醒。 模块 docstring 里写的「HermiT/Pellet reasoning」目前并未实现。 要做真校验请用 run_shacl_validation()（SHACL 路线），或等后续版本补上符号推理。 读完这本书，你应该能一眼识别这种「API 面子、占位里子」的代码。

3.5 SKOS：轻量级的受控词表

不是所有知识组织工作都需要 OWL 级的形式化。图书馆的主题词表、产品分类树、 部门技能标签——这些东西只需要「一堆概念 + 层级 + 别名 + 关联」，推理能力是奢侈品。 SKOS（Simple Knowledge Organization System）为它们设计，核心词汇一眼看完：

SKOS 谓语意思
skos:Concept一个概念（节点类型）
skos:prefLabel / skos:altLabel首选名 / 别名（就是第 1 章「名字只是属性」的标准化版本）
skos:broader / skos:narrower上下位（更宽/更窄的概念），两者互为反向
skos:related相关但无层级关系
skos:ConceptScheme整套词表的容器；skos:inScheme 把概念挂进去
skos:notation / skos:definition编码（如分类号）/ 定义
 
ex:MachineLearning a skos:Concept ;
    skos:prefLabel "machine learning"@en, "机器学习"@zh ;
    skos:altLabel "ML"@en, "机器學習"@zh-TW ;
    skos:broader ex:ArtificialIntelligence ;     # 上位概念
    skos:related ex:Statistics ;
    skos:inScheme ex:TechTaxonomy .

SKOS 和 OWL 的分工：SKOS 描述概念（标签、层级，供人浏览和检索）， OWL 规定概念（公理、定义域，供机器推理）。层级语义天差地别—— skos:broader只是「导航意义上的上下位」，没有 subClassOf 的形式化传递与继承承诺， 所以把 SKOS 层级当 OWL 类层级去推理是错误用法。一个项目里两者常共存： 概念词表用 SKOS 管理，实体类型体系用 OWL 表达。

Semantica 对 SKOS 的支持很务实：核心是 词表图的层级完整性守卫—— semantica/utils/skos.py 的 validate_skos_hierarchy() 在写入新的 broader/narrower 边之前做环检测（broader 指向父、narrower 归一化成同一个方向后 DFS 查环），防止词表层级被写成一个环。README 里说的「SKOS vocabulary management with a visual editor」指的就是 explorer 的词表管理界面（第 12 章会看到 explorer/routes/vocabulary.py）。 另外，SKOS 是「名字只是属性」的正式化：同一概念的多语言 prefLabel、altLabel 并存—— 呼应第 1 章的实体同一性讨论。

3.6 本章回顾

  • SHACL 用 shapes（NodeShape 定靶 + PropertyShape 定则）校验数据图， 产出结构化报告；它不改数据、不推理。
  • 违规四元组：focusNode（谁）+ resultPath（哪个属性）+ sourceConstraintComponent（哪类约束）+ resultSeverity（Violation/Warning/Info）。
  • 常用约束：sh:minCount/maxCount（必填/单值）、sh:datatype（类型）、 sh:in（枚举）、sh:pattern（正则）、sh:closed（封闭形状）。
  • OWL 推理 vs SHACL 校验：一个相信数据去补全世界，一个相信约定去挑数据的刺； 工业 KG 两者并用——SHACL 守门，OWL 扩知。
  • Semantica 源码：run_shacl_validation()（pyshacl）是真实现，带 severity 分桶与 人话解释；OntologyValidator.validate() 是占位实现， consistent/satisfiable 是默认值而非检查结论，hermit/pellet 参数未使用。
  • SKOS：Concept + prefLabel/altLabel + broader/narrower + ConceptScheme—— 面向人的受控词表；broader 没有 subClassOf 的形式化语义。Semantica 用 validate_skos_hierarchy() 做层级环检测。
常见误区
  • 把 SHACL 当推理引擎——它只报告违规；想补全事实要回 OWL/RDFS 或规则引擎。
  • 看到 consistent=True 就放心——先确认它是算出来的还是默认值 （Semantica 的 OntologyValidator 目前就是默认值）。
  • 忘记 pyshacl 是可选依赖——run_shacl_validation 需要 pip install semantica[shacl]，裸装包会 ImportError。
  • Warning 也当致命错误——severity 三档里只有 Violition 让 conforms=false； Warning/Info 是给人看的信号。
  • 拿 skos:broader 做类型推理——SKOS 层级是导航语义，没有 subClassOf 的 传递继承承诺；推理请用 OWL。
