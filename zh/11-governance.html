Chapter 11 · 第三部分：semantica.ontology 深潜

治理与生态：命名空间、版本、模块与 N 元关系

前三章读完了「生成」的主干；本章收割周边生态——让本体成为可长期治理资产 的那一圈设施：NamespaceManager（IRI 铸币厂）、change_management （版本管理）、ModuleManager/DomainOntologies（模块化与领域模板）、 AssociativeClassBuilder（N 元关系建模术）、OntologyEngine（统一门面）与 LLMOntologyGenerator（补上数据推断不了的公理）。第 4 章方法论的每一格， 在这里都能找到代码。

学习目标
  • 能用 NamespaceManager 生成 speaking IRI，并说清 base_uri / 版本 / 元素 IRI 三者的关系（第 4 章黄金法则的落地）
  • 能用 VersionManager 创建版本、比较版本、生成 diff，并说明它为何住在 change_management 子包
  • 能说出 DomainOntologies 的模板机制（get / create / register / list）和 ModuleManager 的用途
  • 能用 AssociativeClassBuilder 把 N 元关系（三方合同 + 签署日期）建成中间类——OWL 的标准解法
  • 能解释 OntologyEngine 门面的价值与 LLMOntologyGenerator 补位的位置（数据推不出的公理）

11.1 NamespaceManager：IRI 铸币厂

第 8 章 Stage 3 和第 10 章的 SHACL 都在调它。NamespaceManager （namespace_manager.py:42）管三件事：铸 IRI、管前缀、管版本。 

from semantica.ontology import NamespaceManager

ns = NamespaceManager(base_uri="https://myco.dev/ontology/",
                      version="1.2.0",
                      use_speaking_iris=True)     # 默认 True：人可读的 IRI

ns.generate_class_iri("Organization")     # → "https://myco.dev/ontology/Organization"
ns.generate_property_iri("worksFor")      # → "https://myco.dev/ontology/worksFor"
ns.register_namespace("risk", "https://myco.dev/risk#")   # 自定义前缀
ns.get_base_uri()                         # 本体 IRI（版本信息住在这里）

关键设计是第 4 章「版本化黄金法则」的直接实现：base_uri 是本体（owl:Ontology 节点）的 IRI，版本挂在它身上；元素 IRI（类/属性）永远无版本——v2 发布后 …/ontology/Organization 不变，跨版本数据不断裂。`use_speaking_iris=True` 时类名直接嵌入 IRI（"会说话的 IRI"），代价是改名即换坐标——所以第 4 章的命名纪律 （NamingConventions）是它的前置守卫。标准命名空间（rdf/rdfs/owl/xsd/skos，第 2 章那张表） 在初始化时自动注册，导出 Turtle 时才有那些漂亮的 @prefix 行。

11.2 change_management：本体的版本管理

VersionManager（semantica/change_management/ontology_version_manager.py:60， 第 5 章说过它从 ontology 搬家至此）围绕 OntologyVersion（:49）对象工作： 

from semantica.change_management import VersionManager

vm = VersionManager()
vm.create_version(ontology, version="2.0.0",
                  description="新增 SanctionedParty 类",
                  backward_compatible=False)      # ← 破坏性变更声明

diff   = vm.diff_ontologies(base_ontology, target_ontology)   # :299 结构级 diff
report = vm.compare_versions("1.0.0", "2.0.0")                # :199 版本对比
vm.list_versions()                                            # :401 版本谱系

三层能力：结构 diff（哪些类/属性新增、删除、修改）、 版本对比报告（兼容性影响）、多版本共存（版本隔离 + import 闭包）。 为什么值得独立子包？因为「本体的变更管理」和「本体的生成」生命周期不同： 生成是流水线一步，变更是治理流程——需要 change log（change_log.py）、 持久化（version_storage.py）这些独立演化的配套。模块边界跟着职责走， 这是第 13 章贡献地图的预演。

11.3 模块化与领域模板

大本体不该是一个巨石文件。ModuleManager / OntologyModule 支持把本体拆成模块（如 core + finance + risk），各自命名空间、组合导入； 配合第 4 章的 ReuseManager（复用外部本体）构成「本体工程的开源生态位」。

DomainOntologies（domain_ontologies.py:39）则提供预置领域模板—— 常见领域（金融、医疗、法务等，list_domains() 可查）的起步本体： 

from semantica.ontology import DomainOntologies

dom = DomainOntologies()
tpl = dom.get_domain_template("finance")     # 取模板（类/属性骨架）
ont = dom.create_domain_ontology("finance")  # 基于模板实例化
dom.register_domain_template("logistics", my_template)   # 注册自家模板

定位是「从零建本体的起跑线」：与其从空目录开始，不如从领域模板裁剪—— 这正是第 4 章「优先复用」铁律的产品化。模板 + 方法论（CQ 驱动裁剪）+ 流水线 （数据推断补充实例侧证据）三者配合，而不是互相替代。

11.4 AssociativeClass：N 元关系的建模术

一个经典建模难题：合同 C-001 由 Acme、Globex 两家共同签署， 签署日不同、各自角色不同。二元关系（subject-predicate-object）装不下—— 一个谓语只有两个端点。N 元关系需要「中间类」模式：把关系本身升格为类。 AssociativeClassBuilder（associative_class.py:74）把它做成了 API： 

from semantica.ontology import AssociativeClassBuilder

builder = AssociativeClassBuilder()
contract_party = builder.create_associative_class(
    name="ContractParty",
    participants=["Acme", "Globex"],
    properties={"signed_on": "xsd:date", "role": "xsd:string"},  # 关系自己的属性
)   # :130

position = builder.create_position_class(         # :206  任职关系（人-职位-组织 三元）
    person="Alice", organization="Acme", title="CTO")
event = builder.create_temporal_association(      # :264  带时间窗的关联
    entities=["Alice", "Acme"], valid_from="2024-03-01")

用第 1 章的话说：中间类把「边」变成了「节点」，于是边也能带属性、也能被查询、也能挂 provenance。 这个模式在 OWL 世界无处不在（PROV-O 的 Activity、第 6 章去重的 DuplicateGroup 本质都是它）。

11.5 OntologyEngine 门面与 LLM 增强

OntologyEngine（engine.py:16）是统一的门面（facade）： from_data()（数据推断路线）、from_text()（LLM 直接从文本起草）、 infer_classes/infer_properties、create_alignment/get_alignments （跨本体对齐）、to_shacl/export_shacl/validate_graph——一条龙。 门面的价值：应用代码只认一个入口，内部组件（生成器/验证器/对齐器）可替换。

LLMOntologyGenerator（llm_generator.py:9）补的是第 9 章明确说过的空档： 数据频率能推出「有哪些类、谁连谁」，推不出领域公理—— 「Manager 和 Intern 互斥」「parent 传递」这类知识不在数据的统计形状里，在领域专家的脑子里。 LLM 路线让这类公理有个人机协作的入口（起草 → 人审 → 入库）。 但注意定位：它是可选增强，与「确定性基础设施」的根基并行—— 默认流水线零 LLM 依赖（第 6 章的抽取三后端同理），用不用 LLM 是你的架构决策。

11.6 本章回顾

  • NamespaceManager：铸 IRI（speaking IRI 默认开）、管前缀、管版本； 版本挂本体 IRI、元素 IRI 永远无版本（第 4 章黄金法则的实现）。
  • VersionManager（change_management 子包）：create_version / compare_versions / diff_ontologies / list_versions；diff + 兼容性声明 + 多版本共存。
  • ModuleManager + DomainOntologies：模块化拆分 + 领域模板起步（get/create/register/list）； 与 ReuseManager 构成本体的「开源生态位」。
  • AssociativeClassBuilder：N 元关系的中间类模式（create_associative_class / create_position_class / create_temporal_association）——关系升格为节点，边就有了属性。
  • OntologyEngine 门面统一入口；LLMOntologyGenerator 补数据推不出的公理 （可选增强，默认流水线零 LLM）。
常见误区
  • 在元素 IRI 里塞版本号——NamespaceManager 的设计就是防这个；版本去本体 IRI。
  • 给 speaking IRI 起中文名/带空格的名——NamingConventions 与第 10 章 _mint_term_iri 的百分号编码都在补这个坑；起名要过规范。
  • 把 N 元关系硬塞成多个二元边——日期/角色没地方挂，数据完整性碎一地； 用中间类。
  • 忽视 backward_compatible 声明——破坏性变更不声明，下游版本对比报告就成了摆设。
  • 把 LLMOntologyGenerator 当默认生成器——它补公理的草稿，不是主流水线； 数据驱动的推断（第 9 章）才是根基。
