类与属性推断：ClassInferrer 与 PropertyGenerator

第 8 章的流水线里有两个被委派出去的黑盒：Stage 2 的 ClassInferrer 和 Stage 3 的 PropertyGenerator。本章打开它们——你会发现「自动本体生成」 的魔法其实是几条朴素而结实的统计规则：频率门槛、Counter 计数、命名启发式、 类型格。也会再次遇到「文档说的算法」与「代码做的算法」的落差： 相似度合并与传递闭包，宣传里有，代码里没有。

学习目标
  • 能完整复述类推断算法：分桶 → 频率门槛（min_occurrences）→ 类定义生成（命名归一 + 50% 公共属性）
  • 能解释层级推断的「拆词找父 + 通用父类兜底」启发式，以及 DFS 环检测的必要性
  • 能说出 similarity_threshold 参数的真实状态（收下但从未使用）
  • 能手工执行属性推断：关系 → ObjectProperty（domain/range 聚合）、实体属性 → DatatypeProperty（XSD 类型格拓宽）
  • 能针对具体数据集调整 min_occurrences 并预判本体质量的变化

9.1 类推断：频率投票决定谁配成为类

ClassInferrer.infer_classes()（class_inferrer.py:96）的算法 可以用一句话讲完：按 entity type 分桶数实例，过得了频率门槛的类型升级为类。 核心判断在 158 行：if len(type_entities) >= self.min_occurrences。 默认门槛 min_occurrences=2——只出现一次的类型（通常是抽取噪声， 比如把 "Money" 金额误标成实体类型）直接出局。

固定的一批实体类型计数（Person×8、Organization×5、Contract×2、Money×1、Product×1）。 拖动滑杆改变 min_occurrences，看哪些类幸存。

拖动滑杆。

过了门槛的类型由 _create_class_from_entities()（253 行）铸成类定义，三个动作：

  1. 命名归一：naming_conventions.normalize_class_name(entity_type)—— 第 4 章的命名纪律在这里自动执行（如 "contract party" → "ContractParty"）；
  2. 公共属性提取（278–302 行）：用 Counter 统计实体 dict 的键 （排除 id/type/text 等元键），只保留至少 50% 实体都有的键—— 偶发字段不进类定义；
  3. 记谱：entity_count 和 metadata.inferred_from—— 类的出身可追溯（呼应第 4 章「决策留痕」的方法论）。

一处必须指出的细节（第 8 章 #1103 的源头）：266–268 行在没有 namespace_manager 时把 "uri" 设为 None——键存在但值为假， downstream 的 not in 守卫因此失效。修好之后 Stage 3 的兜底（if not cls.get("uri")） 挡住了它，但你读代码时应该能认出这种「潜伏字段」。

9.2 层级推断：拆词启发式与环检测

build_class_hierarchy()（184 行）给扁平类列表装 subClassOf。 亲子关系从哪来？_find_parent_class()（304–323 行）是个诚实的朴素启发式： 

# 伪码还原（:309-323）
words = class_name.split()                       # "Contract Party" → ["Contract", "Party"]
for i in range(len(words)-1, 0, -1):             # 从去掉最后一个词开始试
    if "".join(words[:i]) in class_map:          # "Contract" 恰好是个已存在的类？
        return "Contract"                        # → 认作父类
for parent in ["Entity", "Thing", "Resource"]:   # 兜底：通用父类
    if parent in class_map: return parent
return None                                      # 没有父类 → 顶层类
⚠ 文档 vs 代码：相似度合并与传递闭包，宣传里有、代码里没有

ontology/__init__.py 的模块 docstring 宣称层级构建包含 「similarity-based class merging (threshold matching)」和 「transitive closure calculation」；构造函数也确实收 similarity_threshold=0.8 参数（:94 赋值给 self）。 但全文搜索的结果：similarity_threshold 在赋值之后从未被引用， 「transitive」「closure」字样在 class_inferrer.py 里一次都不出现。 真实的层级推断就是上面的拆词启发式。similarity_threshold 目前是 装饰性参数——改它不会有任何效果。给 repo 提 PR 的好机会（第 13 章会再提）。

启发式虽朴素，环检测是动真格的：_check_circular_hierarchy() （379 行起）建 parent_map 后跑 DFS（395 行的嵌套 has_cycle 函数，带 visiting 集合防重入）， A ⊑ B ⊑ A 这种循环继承会被抓出来报 error。为什么必须：RDFS 的 subClassOf 推理是传递的 （第 2 章），一个环会让环上所有类逻辑等价——你的类层级瞬间「降维」。第 3 章的 SKOS 层级环检测 （utils/skos.py）是同一防御的词表版。

完整的 validate_classes()（325–377 行）查三样：重名类（Counter 计数，error）、 命名规范（warning + 建议名）、循环层级（error）。错误和警告分级返回——与第 3 章 SHACL 的 Violation/Warning 分档如出一辙。

9.3 对象属性推断：从关系的两端聚合 domain/range

PropertyGenerator._infer_object_properties() （property_generator.py:133）把第 6 章抽取出的关系变成 ObjectProperty。算法依然是聚合统计：按 relationship type 分组， 每组收集所有出现过的 source 类型 → domain 集合、 所有出现过的 target 类型 → range 集合： 

# :152-185（节选）
domains, ranges = set(), set()
for rel in rels_of_this_type:
    domains.add(rel.source_type)     # works_for 的主语见过 Person、Consultant…
    ranges.add(rel.target_type)      #           宾语见过 Organization…

property_def = {
    "name": "worksFor", "type": "object",
    "domain": list(domains) if domains else ["owl:Thing"],   # 空则兜底 owl:Thing
    "range":  list(ranges)  if ranges  else ["owl:Thing"],
}

这正是第 2 章 domain/range 公理的数据驱动版：不是谁规定的 worksFor 连接 Person 和 Organization，而是数据里每次出现都这么连。两个推论： domain/range 可能是多值的（一个谓语见过多种主语类型）——OWL 完全允许； 数据脏（第 8 章 Stage 1 的 "Entity" 兜底）会让 domain 变成 ["Person", "Entity"] 这种泥沙俱下的集合。

9.4 数据属性推断：XSD 类型格与拓宽规则

_extract_data_properties()（245 行）扫描实体的属性字段（排除元键）， 交给 _infer_property_type()（269–286 行）按类型格映射：

Python 值XSD 类型
True/Falsexsd:boolean
42xsd:integer
3.14xsd:double
匹配日期正则的字符串xsd:date
匹配日期时间正则的字符串xsd:dateTime
其余一切xsd:string

精妙处在 _get_more_general_type()（309 行）：同一属性在不同实体上类型不一致时 （salary 有处是 int 有处是 float），沿格向上拓宽—— boolean < integer < double < date < dateTime < string， 直到装得下所有观测值（最宽到 string）。类型格的偏序设计让「合并冲突类型」变成一次 max 运算。 这是本书第一次遇到格（lattice）结构——推理系统里的常客，记住这个形状。

9.5 推断质量：三条调参心得

  • min_occurrences 是精度/召回旋钮：调高→噪声类出局但稀有真类（Contract?）陪葬； 调低→本体膨胀。经验：先看「只有 1–2 个实例的类型」名单再定阈值，别盲调。
  • 上游质量决定一切：domain 聚合和 "Entity" 兜底直接挂钩。 抽取置信度阈值（第 6 章 NamedEntityRecognizer 的 0.7）是本体质量的第一道闸。
  • 导出前必跑 validate_classes：重名/环/命名三类问题在 dict 阶段修复成本最低； 一旦进了 Turtle 再改，就是 RDF 图手术。

9.6 本章回顾

  • 类推断 = 分桶 + 频率门槛（min_occurrences=2，class_inferrer.py:158）+ 命名归一 + 50% 公共属性提取（Counter）；类的出身记在 metadata。
  • 层级推断 = 拆词找父启发式 + Entity/Thing/Resource 兜底（:304-323）； similarity_threshold 收而不用，宣传的相似度合并/传递闭包代码里不存在。
  • 环检测动真格：DFS + visiting 集合（:395）抓循环继承——subClassOf 传递性下 一个环让全环类等价。
  • 对象属性推断：按关系类型分组，domain=出现过的 source 类型集合、 range=出现过的 target 类型集合，空则 owl:Thing（property_generator.py:152-185）。
  • 数据属性推断：值类型 → XSD 类型格（boolean<integer<double<date<dateTime<string）， 冲突时向上取最小上界（:309）——格结构第一次登场。
  • 质量三心得：阈值看名单再调；上游置信度是第一道闸；导出前 validate_classes。
常见误区
  • 调 similarity_threshold 期望改变合并行为——装饰性参数，无任何效果。
  • 指望层级推断有语义理解——它只认名字里的词，"Employee" 不会自动成为 "Person" 的子类（词不包含）。语义层级要靠复用外部本体（第 11 章 ReuseManager）或人工。
  • min_occurrences=1——抽取噪声全体升格为类，本体变成类型垃圾桶。
  • 把多值 domain 当 bug 修——OWL 允许多 domain；真问题是里面混了 "Entity" 泥沙， 修上游而不是删值。
  • 跳过 validate_classes 直接导出——环和重名在 Turtle 里修复成本翻十倍。
