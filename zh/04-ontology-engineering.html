Chapter 4 · 第一部分：本体领域基础

本体工程方法论

前三章你掌握了语言（RDF/RDFS/OWL/SHACL/SKOS）。但语言不等于工程—— 「会写 Turtle」和「建出一个有用的本体」之间隔着方法论。 本章讲领域里沉淀下来的标准姿势：能力问题驱动、优先复用、命名与粒度纪律、版本化演进。 每一块都对照 Semantica 的对应实现（它们不约而同都长在这个 repo 的 ontology 模块里，不是巧合）。 读完这章，第一部分收官，你具备了读第二、三部分所需的全部领域底子。

学习目标
  • 能为本体项目写出 5–8 条合格的能力问题（Competency Questions），并解释它们如何划定本体边界
  • 能执行本体复用决策：调研（FOAF/Dublin Core/Schema.org 等）→ 对齐评估 → reuse / partial / reject 三选一
  • 能应用命名规范（类 PascalCase 单数名词、属性 camelCase 动词短语）并说明为什么这种纪律值得自动化
  • 能判断一个本体的粒度问题（过粗/过细），并知道「按能力问题够用就好」的原则
  • 能说清本体版本化的 IRIS 最佳实践：版本放本体 IRI 里，不污染元素 IRI

4.1 为什么本体需要「工程方法」

本体项目的死法高度雷同。三种最常见：

  • 过度工程：团队兴奋地建了一个「关于一切」的本体——三百个类、两千个属性， 覆盖了五年后才可能用到的场景。六个月后没人维护，数据一个没进来。领域里叫这个 「本体赶超现实」（ontology over-engineering）。
  • 范围蔓延：从「合同管理本体」滑向「法务领域本体」滑向「公司法本体」。 没有边界声明的项目必然蔓延。
  • 无人使用：建模的人从没问过消费者——查询的人、下游系统—— 这个本体到底要支持什么。交付时才发现关键问题答不了。

领域先驱们（Uschold & King 的企业本体方法、Gruninger & Fox 的 TOVE 方法、 后来 Noy & McGuinness 的「七步法」）给出的解药高度一致，可以浓缩成一个循环：

4.2 能力问题（Competency Questions）：先问「要回答什么」

能力问题（CQ）是 Gruninger & Fox 在 TOVE 方法里提出的概念，如今是行业标准： 在建模之前，用自然语言写下「这个本体建成后，必须能回答哪些问题」。 CQ 是本体的功能需求——它们决定边界（答不上 CQ 的领域角落不建）、 决定验收（拿 CQ 当测试用例）、决定粒度（问题问多细，模型建多细）。

好 CQ 长什么样（合同管理本体示例）
  • 「某公司当前是哪些合同的一方？」——具体、可测试、直接指向类和关系
  • 「某合同在给定日期的生效状态是什么？」——引出时间维度建模
  • 「哪些合同的签约对手方处在受制裁国家？」——引出跨源数据关联

反例：「合同有什么信息？」（太泛，什么模型都能说答了）、「系统性能如何？」（不是本体的问题）、 「AI 会取代律师吗？」（与本体的类和属性无关）。

Semantica 把 CQ 做成了可执行的一等公民（semantica/ontology/competency_questions.py）： 

from semantica.ontology import CompetencyQuestionsManager

manager = CompetencyQuestionsManager()
manager.add_question("Who are the employees of a given organization?",
                     category="organizational", priority=1)   # priority: 1=高 2=中 3=低

results = manager.validate_ontology(ontology)   # 逐条检查本体能否回答
manager.trace_to_elements(question, ontology)   # 问题 → 涉及哪些类/属性
manager.generate_report(ontology)               # 覆盖率报告

数据结构上，CompetencyQuestion（第 42 行起）就是问题文本 + 类别 （general / organizational / temporal）+ 优先级 + answerable 标记 + trace_to_elements 列表。RequirementsSpecManager （requirements_spec.py）再把 CQ 装进完整的需求规格： 领域边界、实体类型范围、目的文档，外加 trace_requirements() 做 「需求 → 本体元素」的追溯。这两样合起来，就是上图第 1、2、5 格的代码化。

4.3 站在巨人肩膀上：本体复用

方法论第二铁律：先找现成的，再造自己的。给「人」建模之前不知道 FOAF 存在、 给「文档元数据」建模之前没看过 Dublin Core、给「公司/产品」建模时忽略 Schema.org—— 这些都是让未来互操作哭泣的决定。复用的收益不只是省事：用公共词表意味着别人的数据能直接对上你的。

标准复用决策三选一（这也是 Semantica ReuseDecision.decision 字段的取值）：

  • reuse：直接引入整个外部本体/模块，用自己的命名空间引用其术语；
  • partial：只对齐部分概念（如只用 FOAF 的 Person 定义，不用其社交属性）；
  • reject：不合用，自建——但必须记录拒绝理由，否则半年后有人再问一遍。

semantica/ontology/reuse_manager.py 实现了完整的复用工作流，还内置了 「知名本体目录」（FOAF、Dublin Core、Schema.org）： 

from semantica.ontology import ReuseManager

manager = ReuseManager()
info      = manager.research_ontology("http://xmlns.com/foaf/0.1/")  # 调研：元数据提取
alignment = manager.evaluate_alignment(source_uri, target_ontology)  # 概念对齐评分
interop   = manager.assess_interoperability(source_uri, target)      # 互操作收益评估
ontology  = manager.import_external_ontology(source_uri, target)     # 导入（含命名空间合并）
manager.track_reuse_decision(uri, decision="partial",
                             reason="只用 Person 定义", ...)          # 决策留痕

ReuseDecision（第 43 行起）记录 source_uri、decision、reason、 imported_elements、compatibility_score——把「为什么当时这么决定」变成数据。 甚至还有 convert_non_ontological_resource()：把 CSV 代码表这类 非本体资源转换成本体——现实中大量「词表」一开始就是 Excel。

4.4 命名与粒度：小规矩，大秩序

本体是给别人读的。命名混乱的本体（PersonInfo vs person_data vs PEOPLE 三个类并存）每个后来者都要付理解税。社区沉淀的规范意外地一致：

元素规范正例反例
类名PascalCase + 单数名词短语Organizationorganizations、ORG
对象属性camelCase + 动词短语/介词worksForwork_for、WorksFor
数据属性camelCase + 名词hasTitleTitle
本体名小写连字符（文件/IRI 段）contract-ontologyContract Ontology!

「类用单数」值得单独说：类是概念的集合定义，Organization 读作「每一个组织」； 复数名 Organizations 会让人分不清它是类还是容器实例。这些规则琐碎到人肉执行必崩， 所以要自动化——Semantica 的 NamingConventions （semantica/ontology/naming_conventions.py）提供 validate_class_name / validate_property_name / suggest_class_name / normalize_class_name 全套（校验不过自动给建议名），本体生成流水线在推断出类名后 逐个过一遍（第 9 章会看到它在 ClassInferrer 里的调用点）。

输入即检查。

粒度是另一条纪律：模型该建多细？两个失败方向——过粗 （一个 Party 类装下人和公司，CQ「某公司的员工」答不利索）和过细 （给邮箱按域名分了八个子类，没有任何 CQ 需要它）。裁决标准回到 CQ： 问题问多细，模型建多细；没有问题需要的深度，就是过度设计。 Semantica 的 OntologyEvaluator（第 11 章展开）甚至量化了这件事—— 粒度得分（granularity score）与泛化/特化分析。

4.5 本体是活的：版本化与演进

本体一旦有数据在上面跑，改动就不再是自由操作：删掉一个类，别人 SPARQL 查询当场失效； 改一个属性的含义，历史数据的解释跟着变。所以成熟的本体工程有专门的版本纪律。 最重要的一条 IRI 最佳实践（也是 Semantica NamespaceManager 实现的）：

版本化 IRI 黄金法则

版本号放本体 IRI 里，不放进元素 IRI。 即：https://example.org/ontology/contract/v2 是本体（ owl:Ontology 节点）的 IRI， 而 …/contract/v2#Organization 这种带版本的元素 IRI 是反模式——正确做法是 元素永远用无版本 IRI（…/ontology/core#Organization），版本关系通过 owl:versionIRI、owl:priorVersion、owl:backwardCompatibleWith 在本体节点上声明。

原因：元素 IRI 是全球坐标（第 1 章）；坐标一旦含版本，v1 和 v2 的同名类会被视为 不同实体，跨版本数据全部断裂——除非你到处补 sameAs。

Semantica 里版本管理经历了模块迁移：VersionManager 和 OntologyVersion 原来住在 ontology 包里，后来移到了独立的 semantica.change_management 模块 （ontology/__init__.py:170-171 有条注释专门说明此事——读源码时这种「搬家留言」 是理解模块演化史的线索）。它提供版本创建、diff 生成、迁移路径识别、多版本共存 （版本隔离 + import 闭包解析）。第 11 章精读。

4.6 本章回顾（兼第一部分收官）

  • 本体项目三大死法：过度工程、范围蔓延、无人使用；方法论循环是解药—— 定范围 → 能力问题 → 复用调研 → 建模 → 用 CQ 验证 → 版本化演进。
  • 能力问题是本体的功能需求：具体、可测试、优先级分层； Semantica 的 CompetencyQuestionsManager 让 CQ 可执行（验证/追溯/报告）。
  • 复用决策三选一：reuse / partial / reject，决策与理由必须留痕； 先看 FOAF / Dublin Core / Schema.org。对应 ReuseManager。
  • 命名纪律：类 PascalCase 单数名词、属性 camelCase；粒度由 CQ 决定—— 没有问题需要的深度就是过度设计。对应 NamingConventions、OntologyEvaluator。
  • 版本化黄金法则：版本在 ontology IRI，不在元素 IRI； owl:versionIRI / priorVersion / backwardCompatibleWith 声明关系。对应 change_management.VersionManager。
  • Semantica 的 ontology 模块结构 = 这套方法论的逐格实现。带着这张地图进第二、三部分。
常见误区
  • CQ 当装饰——写完就锁进文档，不拿来验证。CQ 不跑等于没写。
  • 重造 FOAF 轮子——自造 hasName 而不用 foaf:name， 代价是失去整个生态的互操作。
  • 元素 IRI 带版本号——v1/v2 同名类变成不同实体，跨版本数据断裂。
  • 按数据列名命名类——TblCustomers 不是概念，是表的影子； 本体建模概念，不是镜像表结构。
  • 「先把本体建完美再接数据」——正确顺序是 CQ → 最小可用模型 → 数据进来 → 用 SHACL 报告和 CQ 验证驱动迭代（Semantica 整个产品哲学就是「从数据生长出本体」）。
