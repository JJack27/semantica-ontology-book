Chapter 12 · 第三部分：semantica.ontology 深潜

本体在平台中的位置：反哺、导出、安全与界面

ontology 模块不是孤岛。本章看它如何在平台四处伸出触角：向上反哺分块 （ontology-aware chunking）、向外定义导出词汇表（semantica.dev/ns）、 守住序列化的安全边界（一个 2026 年 8 月刚修的注入漏洞）、以及顶到用户界面的 Ontology Hub。四个集成点各是一个经典工程主题：闭环、契约、安全、人机协作。

学习目标
  • 能解释 ontology-aware 分块如何让「模式层反哺数据层」，以及它与 entity_aware 的分工
  • 能说出 semantica.dev/ns 平台词汇表的「不发明术语」原则及其可信度价值
  • 能描述 Turtle/N-Triples IRIREF 注入漏洞的原理与修复方式——为什么序列化是安全边界
  • 能列出 Ontology Hub（explorer/routes/ontology.py）提供的工作流（草稿/提案/对齐/版本/SHACL）

12.1 ontology-aware 分块：模式层反哺数据层

第 6 章讲分块时提过 ontology_aware 方法（split/kg_chunkers.py:321 的 OntologyAwareChunker，核心函数 split_ontology_aware）。它的独特之处在于 方向反转：其他分块方法只看眼前的文本，ontology_aware 还要参考已有的本体—— 按类与属性的边界切块，让每个分块尽量完整覆盖「关于某类实体的叙述」。

这就是「反哺」：第 8–9 章从数据长出本体，这里本体反过来指导新数据的加工。 两层配合的意义在 GraphRAG 检索链：查询命中一个块 → 块里实体已按类聚集 → 顺着本体的类/属性定义扩展检索（同一类的其他实例）。数据层长出模式层，模式层再把 数据层的加工照亮——全书的主线论断在这里有了第一个具体循环。

12.2 RDF 导出与平台词汇表 semantica.dev/ns

导出（semantica.export.RDFExporter 等）要回答一个本体问题： 「Semantica 自己导出的 RDF 里，那些非标准谓语（sem:xxx）是谁定义的？」答案在 semantica/ontology/vocabulary/semantica-ns.ttl——平台自己的词表， 声明 sem: 前缀下的每个术语：sem:Entity（无类型实体的兜底类）、 sem:Relationship（JSON-LD 导出里被具体化的关系：sem:type/source/target）、 sem:KnowledgeGraph（JSON-LD 顶层文档类型）……

这个文件最值得学的是它的自我克制声明（rdfs:comment 原文大意）： 「以下每个术语都出现在包今天真实产出的输出中（起草自 0.6.5 版导出调用点）； 没有为了完整性而发明任何术语」。这是第 4 章方法论的「不留想象空间」 在词汇表层面的实践——词表与实现同步、拒绝假大全。读它的类定义（Entity/Relationship/KnowledgeGraph） 还能顺带理解 JSON-LD 导出为什么把关系具体化成节点（第 5 章 KG 字典的关系带属性， 二元三元组装不下——正是第 11 章中间类模式的序列化版）。

12.3 安全边界：一个刚修的 Turtle 注入漏洞

⚠ 案例：commit 220fb10e（2026-08-24，就在昨天）

标题：fix(export): escape IRI-valued metadata to close a Turtle/N-Triples injection gap。漏洞：RDF 导出器把 IRI 型的元数据值 （当前只有 sem:sourceUri，来自实体的 metadata["uri"] 键） 直接拼进 <{value}>——零转义。

为什么危险？Turtle/N-Triples 的 IRIREF 语法禁止控制字符、空格、 < > " { } | ^ \` \ 不经转义出现。一个恶意构造的元数据值 （比如包含 " . 之类语法字符的 URI）可以在序列化产物里注入额外的三元组， 甚至破坏整个文档的语法——攻击者的数据借导出之手写进了你的审计档案。

修复：对这些字符做转义后才写入 IRIREF。教训（本repo 专家必修）： 「数据 → RDF 文本」的每一步序列化都是安全边界。 只要值来自外部（文档、元数据、合并进来的实体），就可能携带语法武器； 第 2 章 _mint_term_iri 的百分号编码、这里 IRIREF 转义，是同一原则在不同语法层的落点。 你现在读的这本书成书前一天，这条边界刚被补上——安全是持续过程，不是完成时。 

# 漏洞形态（修复前，伪码）
g.add((subj, SEM.sourceUri, URIRef(metadata["uri"])))
# 序列化时 URIRef 直接变 <{value}> —— 值里若含 " . < > 等字符
# → 攻击者可以在你的 Turtle 里"续写"三元组

# 修复后：值先按 IRIREF 语法转义（控制字符/空格/<>"{}|^`\ 全部处理）
# 序列化产物恢复为「数据只能当数据，永远不能当语法」

12.4 Ontology Hub：本体工作台的用户界面

README 里的「Ontology Hub · SHACL Studio · 可视化编辑器」落在 explorer/routes/ontology.py——一个 FastAPI 路由（/api/ontology 前缀）。 扫一眼它的内部结构（:527-722），能看出一个完整的人机协作治理工作流：

  • 本体注册表（_get_registry，:527）——已导入本体的会话态登记；
  • 对齐存储（_get_alignment_store，:533）——跨本体概念对齐 （第 11 章引擎的对齐能力在界面侧的落点）；
  • 草稿与提案（_get_drafts / _get_proposals，:539/:545）—— 本体修改的 draft → proposal 审批流：改动不直接生效，走提案评审 （第 4 章「决策留痕」的界面化）；
  • 版本列表（_get_versions，:551）——第 11 章 VersionManager 的展示层；
  • SHACL 校验端点——带 asyncio.Semaphore 并发闸（:136）： pyshacl 校验是 CPU 重活，信号量防止并发请求压垮工作台；
  • 图可视化转换（_convert_ontology_to_graph，:638）—— 本体 dict → 前端图的节点/边列表，配命名空间提取（:714）与节点类型分类（:588）。

一个诚实的工程观察：这些 store 都是进程内存字典（Dict[str, OntologyEntry]）—— 重启即清空，多副本不共享。作为「工作台/草稿区」合理，作为持久化治理库不够 （那是 change_management 的 version_storage 的活）。判断一个 HTTP API 的持久化语义， 看它的存储类型比看路由名可靠——这是第 3 章以来「读代码不信标签」的又一次应用。

配套的还有 explorer/routes/vocabulary.py（SKOS 词表管理界面， 第 3 章 validate_skos_hierarchy 守卫的写入端）和 CLI 的 semantica ontology 命令组—— 同一套能力在 Python API / REST / 界面 / CLI 四个入口各有其形（第 5 章的入口矩阵到此闭环）。

12.5 本章回顾

  • 反哺闭环：ontology_aware 分块（kg_chunkers.py:321）用已有本体指导新数据切块—— 模式层照亮数据层的加工，检索链因此受益。
  • 平台词汇表 semantica.dev/ns：只声明包今天真实产出的术语，「不为完整性发明」； sem:Relationship 的具体化是中间类模式的序列化版。
  • 序列化即安全边界（commit 220fb10e）：IRI 型元数据未转义直接进 <…> 允许注入三元组；修复=按 IRIREF 语法转义。 外部数据永远可能携带语法武器。
  • Ontology Hub（explorer/routes/ontology.py）：注册表/对齐/草稿→提案审批流/ 版本/SHACL 端点（带并发信号量）/图可视化；存储是进程内存字典——工作台语义，非持久化治理库。
  • 同一套本体能力分布在 Python API / REST / Explorer / CLI 四入口——第 5 章入口矩阵闭环。
常见误区
  • 把外部 URI 直接拼进 RDF 文本——注入漏洞的标准成因； 序列化库帮你转义的前提是你走库，手拼字符串没人救。
  • 以为 Explorer 的本体注册表是持久存储——进程内存字典，重启即空； 持久化治理在 change_management。
  • 忽略 SHACL 端点的并发闸——pyshacl 是 CPU 密集型，Semaphore 限的是工作台不被压垮。
  • 把 sem: 词表当标准词表引用——它是平台自有导出词汇（0.1.0-draft）， 互操作时公共词表（schema.org 等）仍是首选。
