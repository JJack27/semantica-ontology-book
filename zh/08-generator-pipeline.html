OntologyGenerator：六阶段流水线精读

主角登场。semantica/ontology/ontology_generator.py 是 ontology 模块的发动机 （也是最大的单文件），把第 6 章造出来的 KG 字典变成带类、属性、层级、IRI 的本体。 本章逐段读 generate_ontology()（第 116–224 行）及其四个阶段方法， 顺手揪出三处「文档口径不一」——包括那个号称 HermiT/Pellet 的第 6 阶段的真实身份。 类/属性推断的算法细节留给第 9 章，SHACL 生成本体留给第 10 章。

学习目标
  • 能复述流水线每一阶段的输入/输出形状与代码位置，画出数据变换图
  • 能解释 Stage 1 对多种实体/关系输入形状的归一策略（dict / 对象 / 元组 / 批量列表）
  • 能说出 Stage 3 给类和属性打 @type 与生成 IRI 的规则，以及 #1103 修复的教训
  • 能准确描述 Stage 5 和 Stage 6 的真实执行状态（一个外包、一个是占位）
  • 能独立使用 generate_ontology / generate_from_graph / optimize_ontology 完成一次生成

8.1 流水线全景：一口吃下 KG 字典

from semantica.ontology import OntologyGenerator

gen = OntologyGenerator(base_uri="https://myco.dev/ontology/")
ontology = gen.generate_ontology({
    "entities":      [{"type": "Person", "name": "Alice"},
                      {"type": "Organization", "name": "Acme"}],
    "relationships": [{"source": "Alice", "target": "Acme", "type": "works_for"}],
})
# → {"uri", "name", "version", "classes": […], "properties": […],
#    "imports": [], "metadata": {class_count, property_count, …}, "validation": {…}}

入口是 generate_ontology()（ontology_generator.py:116）。 注意返回的是本体字典——不是 Turtle 字符串（序列化是 Stage 5 的外包活，8.5 节说）。 主体流程一眼看完（154–218 行）：

  1. _stage1_parse_semantic_network(data) → 语义网络（concepts/entities/relationships）
  2. _stage2_yaml_to_definition(sn) → 类定义（调 ClassInferrer）
  3. _stage3_definition_to_types(defs, entities, relationships) → OWL 类型标注（调 PropertyGenerator）
  4. _stage4_hierarchy_generation(typed) → 组装完整本体（调 build_class_hierarchy）
  5. Stage 5（TTL 生成）不在本方法内执行；Stage 6（验证）默认开，调 validator.validate()

值得欣赏的工程细节：每阶段用 progress_tracker 上报进度、每阶段输出都是纯 dict—— 可单测、可断点、可在任何一步接管。读大文件先读主流程方法的骨架，这个文件是好范本。

8.2 Stage 1：语义网络解析——消灭输入形状的巴别塔

_stage1_parse_semantic_network()（241 行起）干的活和第 6 章摄取层惊人地相似： 在系统边界把混乱输入归一。因为它面对的上游五花八门——KG 字典（dict）、 NER 的 Entity 对象、老的元组格式、甚至批量嵌套列表。归一逻辑（255–302 行）：

  • dict → 原样通过；
  • 有 label/text 属性的 Entity 对象 → 转 dict（补 start_char/end_char/confidence/metadata）；
  • [text, label] 二元组 → {"name": text, "type": label}；
  • 列表的列表 → 递归拍平（283–298 行特判「批 NER 输出」）。

然后是本阶段的核心产物概念分组（304–310 行）：按 entity type 归桶—— 

concepts = {"Person":       {"instances": [alice, bob, …], "relationships": […]},
            "Organization": {"instances": [acme, …],          "relationships": […]}}

关系归一同样宽容（313–354 行）：dict / (subject, predicate, object) 对象 / 三元组列表都收。 最有意思的是 363–378 行的端点类型回查：关系只写了 source: "Alice" 没写 source_type 时，拿名字回实体表找类型——找不到就默认 "Entity"。 这个兜底直接决定了第 9 章 domain/range 推断的上限：垃圾进，垃圾出在 Stage 1 就定了调。

8.3 Stage 2–3：类定义 → OWL 类型标注

Stage 2（_stage2_yaml_to_definition，395 行）很薄： 调 self.class_inferrer.infer_classes(entities) 得到类定义列表 （{"name", "label", …}，算法第 9 章精读），附上 generated_at 和 concept_count 元数据。 名字里的 "YAML" 是历史遗物——docstring 与模块注释沿用了早期「概念 → YAML 定义文件」的设想， 现实现直接是内存 dict。这属于读名不读实会吃亏的典型。

Stage 3（_stage3_definition_to_types，421 行）做三件事： 

# 439-441：属性推断（第 9 章主角）
properties = self.property_generator.infer_properties(
    entities=entities, relationships=relationships, classes=classes)

# 447-450：类打类型 + IRI
for cls in classes:
    cls["@type"] = "owl:Class"
    if not cls.get("uri"):
        cls["uri"] = self.namespace_manager.generate_class_iri(cls["name"])

# 453-460：属性按宾语类型分流 + IRI
for prop in properties:
    prop["@type"] = "owl:ObjectProperty" if prop["type"] == "object" else "owl:DatatypeProperty"
    if not prop.get("uri"):
        prop["uri"] = self.namespace_manager.generate_property_iri(prop["name"])

第 2 章学的 OWL 属性三分在此落地：prop["type"] == "object"（宾语是资源） → ObjectProperty，否则 DatatypeProperty。IRI 由 NamespaceManager 统一生成 （第 11 章精读其 base_uri + speaking-IRI 逻辑）。

源码里的 bug 化石：#1103 注释（443–446 行）

447 行上方留着一段注释：ClassInferrer 在没给 namespace manager 时会设 "uri": None，导致键存在、not in 守卫永不触发， 每个类都以「无 IRI」状态流到导出器（issue #1103）。 修复方式就是你现在看到的 if not cls.get("uri")（falsy 判断替代键存在判断）。 教训两层：① key in dict 与 dict.get(key) 的真值语义差异是 Python 高频坑；② 流水线中「None 也是值」的字段会静默穿透多层—— 越长的管道越要在边界校验。

8.4 Stage 4：层级生成与本体组装

Stage 4（_stage4_hierarchy_generation，468 行）先调 class_inferrer.build_class_hierarchy(classes) 给类列表装父子关系 （相似度推断 + 环检测，第 9 章展开），然后组装最终骨架： 

ontology = {
    "uri":      self.namespace_manager.get_base_uri(),   # 本体 IRI（版本在这里，第 4 章黄金法则）
    "name":     options.get("name", "GeneratedOntology"),
    "version":  self.namespace_manager.version,
    "classes":  classes,       # 已带 @type / uri / subClassOf
    "properties": properties,  # 已带 @type / uri / domain / range
    "imports":  [],            # 预留：外部本体导入（ReuseManager 填）
    "metadata": {class_count, property_count, generated_at, …},
}

这个 dict 就是第 2 章读过的 OWLGenerator.generate_owl(ontology) 的输入形状—— 流水线在两个类之间以 dict 交接，OntologyGenerator 负责「长出内容」， OWLGenerator 负责「穿上 RDF 外衣」。职责切分干净。

8.5 Stage 5 与 Stage 6：名字、现实与三份口径

Stage 5（TTL 生成）不在这个方法里发生。195 行只有一行注释： # Stage 5: TTL Generation (handled by OWLGenerator)。 要拿到 Turtle，你得自己再调一步： 

from semantica.ontology import OWLGenerator
turtle = OWLGenerator().generate_owl(ontology, format="turtle")

Stage 6（符号验证）默认执行，但验了个寂寞。197–211 行： if options.get("validate", True): validation_result = self.validator.validate(ontology)， 结果写进 ontology["validation"]。而 self.validator 是谁？ 第 3 章已经验过尸：占位版 OntologyValidator——hermit 参数没人用、 consistency/satisfiability 是恒 True 的默认值。所以返回体里的 validation.consistent=True 不是「检查通过」，是「没检查」。

⚠ 三份口径，一个真相
  • ontology/__init__.py 模块 docstring：「6-Stage Pipeline， Stage 6 - Symbolic Validation: HermiT/Pellet reasoning」；
  • generate_ontology 的 docstring（118 行）：「Executes the complete 5-stage pipeline」且列表只有 5 项；
  • 同一方法的进度消息（158 行）：「Generating ontology using 6-stage pipeline」。

同一个文件里 5 与 6 并存，模块级宣传语还点名了并未接入的 HermiT/Pellet。 作为 repo 专家，你的正确姿势：信代码不信注释，信注释不信宣传语； 给别人的建议是 generate_ontology(data, validate=False) 关掉占位验证， 需要真校验走 run_shacl_validation()（SHACL，第 10 章）。 顺带一提：这不是「烂 repo」的标志——快速演进的开源项目里文档漂移是常态， 能在代码里读到真相、并且知道去哪读，才是 repo 专家的核心竞争力。

8.6 使用姿势大全

# ① 基本生成（validate 默认 True；建议显式 False，见 8.5）
ontology = gen.generate_ontology(data, name="ContractOntology", validate=False)

# ② 从 GraphBuilder 产物直接生成（别名，:226）
ontology = gen.generate_from_graph(kg_dict, validate=False)

# ③ 只要类 / 只要属性（分别直通 ClassInferrer / PropertyGenerator）
classes    = gen.infer_classes(data)
properties = gen.infer_properties(data, classes)

# ④ 质量优化：OntologyOptimizer（:609）——去重类、合并冗余属性等结构整理
ontology   = gen.optimize_ontology(ontology)

# ⑤ 串联第 2 章的 OWLGenerator 拿 Turtle
turtle     = OWLGenerator().generate_owl(ontology, format="turtle")

8.7 本章回顾

  • generate_ontology()（ontology_generator.py:116）：KG 字典 → 本体字典； 四个阶段方法各自纯函数式（dict 进 dict 出），progress_tracker 全程上报。
  • Stage 1（:241）：输入归一（dict/对象/元组/批量）+ 按 entity type 分桶 concepts + 关系端点类型回查（找不到默认 Entity——推断质量的地基）。
  • Stage 2（:395）：调 ClassInferrer 出类定义；"YAML" 是历史名，现实现是内存 dict。
  • Stage 3（:421）：属性推断 + @type 三分标注（owl:Class / ObjectProperty / DatatypeProperty）+ NamespaceManager 生成 IRI； #1103 注释是「None 值穿透流水线」的 bug 化石。
  • Stage 4（:468）：build_class_hierarchy 装父子关系，组装 uri/name/version/imports/metadata 骨架。
  • Stage 5 不在流水线内（外包给 OWLGenerator）；Stage 6 调的是占位 validator—— 5/6 阶段口径与 HermiT/Pellet 宣传均与实现不符。生产姿势：validate=False + SHACL。
常见误区
  • 以为 generate_ontology 返回 Turtle——返回 dict；序列化要再调 OWLGenerator。
  • 看到 validation.consistent=True 就放心——占位实现的默认值，没有检查发生。
  • 指望 Stage 6 的 HermiT/Pellet——宣传语，未接入。
  • 喂进脏类型就指望好本体——Stage 1 的 "Entity" 兜底会把未识别类型的端点 全归成一桶，层级和 domain/range 全歪。上游规范化（第 6 章）不能省。
  • 忽略 optimize_ontology——推断出的本体常有冗余类/属性，导出前过一遍 Optimizer 是好习惯。
