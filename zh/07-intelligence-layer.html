智能层四件套：Ontology · Reasoning · Provenance · Decisions

流水线造出 KG 之后，四个模块在它之上各加一个维度：ontology 加「模式」、 reasoning 加「推断」、provenance 加「出处」、 decisions 加「因果」。合起来就是架构图里的「Enriched KG」。 本章把四个都过一遍手感（ontology 只点到为止——它是第三部分整块的主角）， 并揭示一个贯穿性事实：四件套的每个能力都在第 1–4 章的理论里有根。

学习目标
  • 能说出四件套各自给 KG 增加的维度，以及它们共享的输入（KG 字典）
  • 能用 ReteEngine 写一条 AML 规则并解释 Rete 网络为什么快（以及 Semantica 实现的已知局限）
  • 能用 DatalogReasoner 写递归规则（ancestor 例），并说明「解释生成」的可问责价值
  • 能用 ProvenanceManager 追溯一个实体的来源（track_entity / get_lineage / trace_lineage）
  • 能描述决策生命周期五步（record → link → query → govern → audit），并区分三个正交查询方向

7.1 四件套协作总览

四个模块都吃同一样东西——KG 字典，各自产出可并回图的结构： ontology 产出类/属性/SHACL（模式层）；reasoning 产出推断出的事实与解释； provenance 产出「每个事实从哪来」的链条；decisions 把 AI 的选择变成带因果边的一等节点。 监管故事「为什么这个 AI 批了这笔贷款」需要四者合奏：决策记录（d）挂推理链（r）， 引用的实体有出处（p），而所有类型/约束来自本体（o）。

7.2 reasoning：确定性推理三引擎

semantica.reasoning 提供三种可解释的推理器，对应第 2 章说的 OWL RL 路线 （公理都化成 if-then 规则，多项式可算）：

① 前向链（Reasoner，reasoning/reasoner.py:57）： 从已知事实出发，反复套用规则直到没有新事实——就是第 2 章 rdfsInference 演示的引擎版。

② Rete 网络（ReteEngine，reasoning/rete_engine.py:120）： 前向链的工业化加速版。朴素前向链每来一个新事实要把所有规则重试一遍； Rete 用「编译好的网络」记住规则的条件匹配状态（alpha 节点过滤单个条件、 beta 节点做跨条件连接），新事实只走受影响的路径——规则多、事实多时快几个数量级。 经典用法是规则引擎式合规检查：

from semantica.reasoning import ReteEngine, Rule, Fact, RuleType

rete = ReteEngine()
rete.build_network([                       # rete_engine.py:155
    Rule(rule_id="aml_flag",
         conditions=[
             {"field": "amount",  "operator": ">", "value": 10_000},
             {"field": "country", "operator": "in", "value": ["IR", "KP", "SY"]},
         ],
         conclusion="flag_for_compliance_review",
         rule_type=RuleType.IMPLICATION),
])
rete.add_fact(Fact("tx_001", "transaction", [{"amount": 15_000, "country": "IR"}]))
flagged = rete.match_patterns()            # rete_engine.py:266
# → [{"rule": "aml_flag", "matched_facts": ["tx_001"], "conclusion": "flag_for_compliance_review"}]
⚠ 文档 vs 代码：Rete 匹配器的已知局限（README 自己承认）

README 在 reasoning 模块下挂了一条醒目的 Current limitation： 「ReteEngine's alpha-node condition matcher is intentionally simple in this release — validate match_patterns() output against your actual rule set before wiring it into a production compliance gate」。翻译：alpha 节点的条件求值目前刻意从简， 上生产合规门之前必须先用自己的规则集验证输出。这是继第 3 章 OntologyValidator 之后 第二处「README 明示的实现局限」——好消息是它明说了；坏消息是很多人不读注释。 本书的态度：知道边界的能力才是可用的能力。

③ Datalog（DatalogReasoner，reasoning/datalog_reasoner.py:39）： 递归规则查询，图上算传递闭包的天然语言：

engine = DatalogReasoner()
engine.add_fact("parent(tom, bob)")
engine.add_fact("parent(bob, ann)")
engine.add_rule("ancestor(X, Y) :- parent(X, Y).")
engine.add_rule("ancestor(X, Z) :- parent(X, Y), ancestor(Y, Z).")   # ← 递归
engine.query("ancestor(tom, ?X)")    # → [{"X": "bob"}, {"X": "ann"}]

第 4 章「能力问题」的推理版实现正在这里：CQ「A 的祖先有谁」⇒ 一条 Datalog 规则。 配套的 ExplanationGenerator（reasoning/explanation_generator.py:95） 把推理过程展开成带步骤的 Explanation 对象——不是只给答案，而是给 「答案是怎么一步步推出来的」。这正是「可问责 AI」的推理侧支柱：黑盒推理在监管场景一文不值。

7.3 provenance：W3C PROV-O 溯源

第 1 章说「每个节点都能回答『我从哪来』」——具体机制是 W3C PROV-O 标准 （entity 被什么 activity 产生、agent 参与了什么）。ProvenanceManager （provenance/manager.py:64）把它落到 SQLite 存储： 

from semantica.provenance import ProvenanceManager

prov = ProvenanceManager(storage_path="./audit.db")
prov.track_entity("acme_corp", source="contracts/acme_master_2024.pdf",
                  metadata={"page": 1, "confidence": 0.97,
                            "extractor": "NamedEntityRecognizer"})   # manager.py:268
prov.track_relationship("alice_works_for_acme", source="hr/employees_q1.csv",
                  metadata={"source_entity_id": "alice_chen", "target_entity_id": "acme_corp"})  # :422

lineage = prov.get_lineage("acme_corp")      # :753  直接来源
trail   = prov.trace_lineage("alice_chen")   # :819  完整祖先链（可限深）

与第 6 章的连线：去重合并时 preserve_provenance=True 保的就是这些记录； 审计导出（PROV-O Turtle / CSV / JSON）的原料也是它。四件套里 provenance 最像「税务局」—— 不生产知识，但每笔交易都留票据。

7.4 decisions：决策智能

决策智能是 Semantica 的旗舰叙事：AI 的每次选择不是一行日志，而是图上一等公民节点， 带五步生命周期： 

graph.record_decision(                       # context_graph.py:4078
    category="credit_application",
    scenario="Personal loan, $85k income, 31% DTI",
    reasoning="Income meets threshold; no adverse credit events",
    outcome="proceed_to_underwriting", confidence=0.88)   # → decision_id

graph.add_causal_relationship(d1, d2, relationship_type="CAUSED")

因果边的类型是封闭枚举：context_graph.py:494 定义 _CAUSAL_EDGE_TYPES = ("CAUSED", "INFLUENCED", "PRECEDENT_FOR")， 且 502–506 行有别名归一表（CAUSES→CAUSED、INFLUENCES→INFLUENCED、PRECEDES→PRECEDENT_FOR）—— 用户手滑写动词形态也能被规整。这个「枚举 + 宽容归一」的小模式在大型代码库里非常值得学。

记录之后的三个正交查询方向：

  • 向上：trace_decision_chain(id) 追完整因果祖先——「为什么会走到这一步」；
  • 向下：analyze_decision_impact(id) 看下游影响面——「这个决定影响了什么」；
  • 横向：find_similar_decisions("...") 语义先例检索——「以前类似情况怎么处理的」。

加上治理与导出（check_decision_rules() 策略门；PROV-O/CSV/JSON 审计导出）， 完整生命周期就是：record → link → query → govern → audit （ARCHITECTURE.md 的五格图）。决策模块横跨 context 包多个文件 （decision_recorder / decision_models / causal_analyzer / policy_engine / decision_query）—— 但统一从 ContextGraph 的方法面暴露。

7.5 ontology 在四件套中的位置：为另外三件提供「语法」

把四件套摆在一起，ontology 的角色就清晰了——它不直接回答业务问题， 它定义另外三件套所引用词汇的语义：

  • reasoning 的规则条件写 amount > 10000，而「transaction 有 amount 字段、 amount 是 xsd:long」是本体的断言；
  • decisions 的 scenario/metadata 里类型化的字段，其合法取值由本体 + SHACL 把关；
  • provenance 记录 extractor 名字，而 extractor 与实体类型的对应关系是本体知识；
  • 四件套产出的增强 KG 最终落进三元组库时，SPARQL 查询的每个谓语 IRI 都来自本体词汇 （第 12 章讲 semantica.dev/ns# 词表时闭环）。

一句话总结全书后半的论点：没有本体的知识图谱是「节点汤」，没有知识图谱的本体是「空中楼阁」—— Semantica 的流水线让两者从彼此中生长。第三部分我们就钻进这个生长机器： OntologyGenerator 如何从 KG 字典推断出类、属性、层级与 SHACL。

7.6 本章回顾

  • 四件套四维度：ontology 加模式、reasoning 加推断、provenance 加出处、decisions 加因果； 全部以 KG 字典为输入，产出并回图 → Enriched KG。
  • reasoning 三引擎：前向链（基础）、Rete（编译匹配网络加速，rete_engine.py:120）、 Datalog（递归规则/传递闭包）。OWA RL 路线的工程落地。已知局限：alpha 匹配器刻意从简， 生产合规门前须自验。
  • provenance：PROV-O 标准 + SQLite 落地；track_entity/track_relationship 记录， get_lineage/trace_lineage 回溯；去重的 preserve_provenance 保的就是它。
  • decisions：决策是一等节点；因果边枚举（CAUSED/INFLUENCED/PRECEDENT_FOR）+ 别名归一 （context_graph.py:494-506）；生命周期 record→link→query→govern→audit； 三正交查询：trace 向上 / impact 向下 / similar 横向。
  • ontology = 四件套的语法层：另外三件引用的每个词汇的语义都由本体定义。
常见误区
  • 把 ReteEngine 直接当生产合规门——README 明示 alpha 匹配器从简，先用自己的规则集验证。
  • 期望推理器替你发现「逻辑矛盾」——Semantica 的推理器是规则引擎路线（加事实）， 逻辑冲突检测在 conflicts 模块（第 6 章）走的是另一条路。
  • 把决策记录当日志写——decision 是图节点：不 link 因果边、不挂 provenance， trace/impact 就退化成空查询。记录时就要连线。
  • 绕过 record_decision 自己建决策节点——绕过统一入口会错过类型约束、 策略门与导出适配。
  • 以为 provenance 只是「记个文件名」——它是结构化的 PROV-O 链 （谁、什么活动、什么置信度、哪一页），审计导出的完整语义都建立在结构化程度上。
